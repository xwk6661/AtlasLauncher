> 范围：`launcher/` 全部 892 个 `.cpp/.h`，重点是本 fork 的新代码 `launcher/maps/`（47 .cpp + 52 .h / 27,327 行合计）、
> `launcher/net/{Request,FileSink,NetJob,DownloadMonitor,DownloadSource}`、`launcher/ResourcePaths`
> 与既有文件的接线点（`Application` / `MinecraftInstance` / `InstanceDirUpdate` / `MainWindow`）。
>
> 方法：静态扫描（危险模式 grep + 逐条读代码确认）+ 工程/资源度量；`ctest` 33/33 作为基线。
> **未做**：动态分析（Windows 上没跑 ASan/TSan，MSVC 也没开 `/fsanitize=address`）、GUI 压测、
> 真机长时间挂机。所以下文"崩溃风险"都是**代码路径上成立**，不是复现过的现场。

## 0. 先说结论

1. **真正需要马上处理的只有 3 条**：一个跨线程共享的静态 `QHash`、两个静态 `QObject` 单例的生命周期、
   以及导入线程里对共享索引/缓存的读改写。三条都在同一片区域（导入 + 大厅 + 封面）。
2. **性能问题集中在"把 3.6 MB JSON 和 GB 级文件搬动放在 UI 线程"**，以及两处用 item-widget 堆出来的列表；
   功能没错，但数据量一涨就是卡顿。
3. **规范层面整体是健康的**：`QT_NO_CONTEXTLESS_CONNECT` 与 `QT_DISABLE_DEPRECATED_UP_TO=0x060800`
   都是编译期硬约束（见 §6），所以"无 context 的 lambda 连接""已废弃 API"这两类常见坑在本项目里
   **根本编译不过**。剩下的规范问题主要是魔法数字、超长函数与两套大厅 UI 的重复。

## 1. 崩溃风险（P0）

### P0-1 `HallCache::findListRow()` 的静态缓存没有互斥，且被工作线程调用

**位置**：`launcher/maps/HallCache.cpp:116-146`

```cpp
static QHash<QString, QJsonObject> rows;   // :121 函数内静态
static QDateTime loadedAt;                 // :122
...
if (rows.isEmpty() || info.lastModified() != loadedAt) {
    rows.clear();                          // :133 工作线程在这里重哈希
    ...
    rows.insert(key, row);                 // :140
}
return rows.value(slug);                   // :145
```

**调用点分属两个线程**：

| 线程 | 调用点 | 场景 |
| --- | --- | --- |
| 线程池（`QtConcurrent`） | `MapImportTask.cpp:553` | 导入时勾了「关联到 CTM 条目」，在 `writeMetadata()` 里查标题 |
| UI | `MapInstanceBar.cpp:405` | 实例窗口右侧地图卡片 |
| UI | `MapLibraryPanel.cpp:1229` | 打开「本地库」时按 slug 取站上行 |

`MapImportTask::writeMetadata()` 跑在 `QtConcurrent::run` 的 lambda 里（`MapImportTask.cpp:173-208`），
所以「导入一张大厅里的图」+「同时打开本地库/实例页」= 一个线程 `clear()`+`insert()`，另一个线程 `value()`。

**影响**：`QHash` 重哈希期间读到半写状态 → 崩溃或返回损坏的 `QJsonObject`；`loadedAt` 与 `rows` 也可能互相错位，
表现为"某个包突然没有站上名字"。概率取决于时序，但导入本身要几十秒，窗口不小。

**建议**：两级锁 —— 锁内只做"命中判断/取值"，解析放在锁外，最后整体换入。

```cpp
namespace {
QMutex g_cacheMutex;
QHash<QString, QJsonObject> g_rows;
QDateTime g_loadedAt;
}  // namespace

QJsonObject HallCache::findListRow(const QString& slug)
{
    if (slug.isEmpty())
        return {};

    const QFileInfo info(path());
    if (!info.exists())
        return {};
    const QDateTime stamp = info.lastModified();

    {
        QMutexLocker lock(&g_cacheMutex);
        if (!g_rows.isEmpty() && stamp == g_loadedAt)
            return g_rows.value(slug);
    }

    // 解析 3.6 MB 不持锁：否则 UI 线程会被导入线程按住
    QHash<QString, QJsonObject> built;
    const HallSnapshot snapshot = load();
    built.reserve(snapshot.listRows.size());
    for (const auto& value : snapshot.listRows) {
        const QJsonObject row = value.toObject();
        const QString key = row.value(QStringLiteral("slug")).toString();
        if (!key.isEmpty())
            built.insert(key, row);
    }

    QMutexLocker lock(&g_cacheMutex);
    g_rows = std::move(built);
    g_loadedAt = stamp;
    return g_rows.value(slug);
}
```

> 更好的做法是把它变成"只读快照"：`HallCache::index()` 返回 `std::shared_ptr<const QHash<...>>`，
> 读者持 shared_ptr，写者整体替换 —— 完全无锁竞争。改动面比加锁大，放进长期。

### P0-2 两个 `static QObject` 单例的生命周期晚于 `QApplication`

**位置**：

- `launcher/maps/MapCoverLoader.cpp:119-123`（`static MapCoverLoader loader;`，析构在 `:108-117`）
- `launcher/net/DownloadMonitor.cpp:40-44`（`static DownloadMonitor monitor;`）

两者都是函数内静态 `QObject`，成员里有 `QTimer` / `QProcess` / `QNetworkAccessManager`：

```cpp
MapCoverLoader::~MapCoverLoader()
{
    if (m_browser != nullptr) {
        m_browser->kill();
        m_browser->waitForFinished(2000);   // :113 退出时在静态析构里阻塞
    }
    QDir(m_browserProfile).removeRecursively();
}
```

**影响**：

1. **退出路径**：静态对象在 `main()` 返回后析构，此时 `QCoreApplication` 已销毁。`QTimer` 停表、
   `QProcess` 收尾都依赖事件循环/全局状态，典型症状是退出时刷
   `QObject::killTimer: Timers cannot be stopped from another thread` 或偶发退出崩溃；
   最坏情况下 `waitForFinished(2000)` 让退出多等 2 秒。
2. **线程亲和**：`instance()` 是谁先调谁创建。现在所有调用点都在 UI 线程（`HallDialog.cpp:194`、
   `MapHallPage.cpp:297/335/1314`、`MapInstancePage.cpp:444/481`），但这是个**隐式契约**，
   以后任意一处从 `QtConcurrent` 里调一次，`QTimer` 就绑到一个没有事件循环的线程上 —— 封面永远不回来。

**建议**：改成"受 `qApp` 管理、首次创建断言 GUI 线程"的懒汉单例，并在 `aboutToQuit` 主动收尾。

```cpp
MapCoverLoader* MapCoverLoader::instance()
{
    Q_ASSERT(QThread::currentThread() == QCoreApplication::instance()->thread());
    static MapCoverLoader* loader = [] {
        auto* l = new MapCoverLoader(QCoreApplication::instance());  // 生命周期交给 qApp
        QObject::connect(QCoreApplication::instance(), &QCoreApplication::aboutToQuit, l,
                         [l] { l->shutdown(); });                     // 停浏览器、停表、清 profile
        return l;
    }();
    return loader;
}
```

`DownloadMonitor` 同理（它没有定时器，但 `m_jobs` 是裸指针集合，见 P0-3）。

### P0-3 导入线程直接读改写共享索引与缓存（丢更新 + 与 P0-1 叠加）

**位置**：`MapImportTask.cpp:475-563`（`writeMetadata()`，运行在线程池）

| 行 | 调用 | 共享状态 |
| --- | --- | --- |
| `:528` | `MapRepository::importIntoLibrary()` | 移动归档到 `maps/` |
| `:544` | `MapLibrary::rememberImported()` | **读-改-写** `map-library.json` |
| `:553` | `HallCache::findListRow()` | 静态缓存（P0-1） |
| `:565` | `MapMeta::save()` | 实例自己的 `map.json`（独占，安全） |

`MapLibrary::rememberImported()`（`MapLibrary.cpp:795-855`）是"读整份索引 → 改一条 → 写回"。
UI 侧的 `MapLibraryPanel` 持有自己的 `MapLibrary` 实例（内存索引），改名/分类/删除时会整份写回。
两边并发时，**后写的一方会覆盖前一方**：导入刚登记的新包可能被面板的下一次保存抹掉，
或者面板里的改名被导入的写回覆盖。

**影响**：数据不一致（新包在库里"消失"、关联丢失），不会立刻崩，但排查成本极高。
和 P0-1 叠加时还可能崩。

**建议**（按代价从低到高）：

1. **进程内串行化索引写入**：给 `MapLibrary` 的 `readIndexObject/writeIndexObject` 加一把文件级
   `QMutex`（静态），所有写路径都走它；写前重新读盘，避免"拿着旧快照覆盖"。
2. 导入完成后由 UI 侧 `refresh()` 重新读盘（`LocalLibraryPage::openedImpl()` 已有，但导入结束当下没有）。
3. 长期：把库索引做成单一拥有者（`MapLibraryStore` 单例，只在 UI 线程读写），工作线程通过信号请求变更。

> 不要用 `Qt::BlockingQueuedConnection` 把写操作弹回 UI 线程：`MapImportTask` 析构时 UI 线程会
> `waitForFinished()`（`:98-100`），工作线程又在等 UI → 死锁。这是本项目里唯一必须避开的组合。

### P0-4 `MapQuitWatcher` 关窗时按 PID 找窗口，存在 PID 复用窗口

**位置**：`launcher/maps/MapQuitWatcher.cpp:48-75`（`closeWindowsOfPid`）、`:211-234`（`closeGame`）

```cpp
if (!m_instance->isRunning()) return;                     // :213 判定还活着
auto* task = m_instance->getLaunchTask();
const qint64 pid = task != nullptr ? task->pid() : -1;    // :217
const int closed = pid > 0 ? closeWindowsOfPid(pid) : 0;  // :220 → EnumWindows 发 WM_CLOSE
```

`isRunning()` 与 `EnumWindows` 之间游戏可能刚好退出；Windows 会回收 PID，若被另一个**有可见顶层窗口**的
进程复用，就会给不相干的程序发 `WM_CLOSE`（轻则关掉别人的窗口，重则丢未保存数据）。

**影响**：概率低（需要毫秒级窗口 + PID 恰好复用），但后果是"启动器关了别的程序"，属于必须堵的类别。

**建议**：先拿进程句柄再枚举，句柄在手期间 PID 不会被复用；并在枚举回调里再核对一次窗口所属进程的
创建时间。

```cpp
const DWORD pid = static_cast<DWORD>(task->pid());
HANDLE proc = OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION | SYNCHRONIZE, FALSE, pid);
if (proc == nullptr)
    return;                       // 已经退了：不要退化成"按 PID 找窗口"
const int closed = closeWindowsOfPid(pid);   // 期间持有 proc
CloseHandle(proc);
```

### P0-5 `BrowserFetch::cleanup()` 在 UI 线程阻塞最多 3 秒

**位置**：`launcher/maps/BrowserFetch.cpp:118-133`（`waitForFinished(3000)`），调用自 `:142`（`get()` 入口）、
`:137`（`abort()`）、`:113-116`（析构）

`get()` 每次开新请求前都会 `cleanup()` 上一个进程。正常情况下进程已退出（`NotRunning`）不会等；
但只要上一次是超时被杀、或浏览器正在自更新，`kill()` 之后仍可能迟迟不退出 —— 这三秒是**同步**的，
界面直接白屏。

**影响**：大厅换源/重试时偶发 2–3 秒卡顿；退出时可再叠加一次。

**建议**：不等，改成"交给 `finished` 自己删"。

```cpp
void BrowserFetch::cleanup()
{
    m_killTimer->stop();
    if (m_proc == nullptr)
        return;
    m_proc->disconnect(this);
    QProcess* dying = m_proc;
    m_proc = nullptr;
    if (dying->state() != QProcess::NotRunning)
        dying->kill();
    QObject::connect(dying, &QProcess::finished, dying, &QObject::deleteLater);
}
```

代价：短时间内可能有两个浏览器进程并存（旧的在被 kill）。用 `m_orphans` 计数上限 2 即可。

## 2. 性能（P1）

### P1-1 大厅列表用 `QListWidget` + 每行一个 `QWidget`

**位置**：`launcher/maps/MapHallPage.cpp:878-886`

```cpp
auto* row = new QListWidgetItem(m_list);
row->setSizeHint(QSize(0, ROW_COVER_H + 20));
auto* widget = new HallRow(item, m_localSlugs.contains(item.slug), m_list);
m_list->setItemWidget(row, widget);
```

每页 20 条、可反复「加载更多」直到 2287 条；每条一个 `HallRow`（含封面 `QLabel`、若干 chip、两三个按钮）。
每个 item-widget 都是一个独立 `QWidget`（有窗口句柄、样式、布局），滚动时全部参与绘制。

**影响**：加载到几百条时滚动明显掉帧；2287 条时内存与首帧代价都不可接受。另外
`refreshLocalMarks()`（`:1334-1341`）每次都用 `itemWidget()` 遍历全部行，加「已入库」标记是 O(n) 的控件访问。

**建议**：`QListView` + `QStyledItemDelegate`（长期），或折中：**上限 + 回收** —— 只保留最近 N 行 widget，
其余用 `QListWidgetItem` 的文本模式；加载更多时把远端行降级（需要额外状态机，不建议）。
真正干净的是 delegate：

```cpp
class HallRowDelegate : public QStyledItemDelegate {
    void paint(QPainter* p, const QStyleOptionViewItem& opt, const QModelIndex& idx) const override {
        const auto& item = m_model->at(idx.row());
        // 直接 drawPixmap(封面) + drawText(标题/系列/评分)，不创建任何 QWidget
        ...
    }
    QSize sizeHint(...) const override { return { 0, ROW_COVER_H + 20 }; }
};
```

### P1-4 资源库迁移把 GB 级复制放在 UI 线程 + `processEvents()`

**位置**：`launcher/maps/MapResourcePage.cpp:354-360`

```cpp
const QStringList errors = ResourceStore::apply(root, m_migrate->isChecked(),
    [&progress](int done, int total, const QString& file) {
        progress.setValue(done);
        QCoreApplication::processEvents();   // :359
    });
```

两个问题叠在一起：①复制几个 GB 期间 UI 线程一直在跑同步 I/O，只能靠 `processEvents` 维持"能重绘"；
②`processEvents` 会重入事件循环，用户可以在迁移进行中触发别的槽（包括关闭设置页），此时 `this` 与
`progress`（栈对象）都可能被销毁 → 潜在 use-after-free。

**影响**：迁移 3 GB 时界面长时间无响应；重入是真实的崩溃路径（虽然窗口模态挡住了大部分操作）。

**建议**：`ResourceStore::apply` 放到 `QtConcurrent`，进度用信号回主线程（与 `MapImportTask` 同一套模式），
取消按钮改回可用（有 abort 位就不会留半套文件）。

### P1-6 导入/重装任务析构时在 UI 线程 `waitForFinished()`

**位置**：`MapImportTask.cpp:98-100`、`:684-686`

```cpp
MapImportTask::~MapImportTask()
{
    m_abortRequested.store(true);
    if (m_extractWatcher.isRunning())
        m_extractWatcher.waitForFinished();   // UI 线程
}
```

注释解释了为什么必须等（worker 捕获裸 `this`），设计本身是对的。但**等待发生在 UI 线程**：
玩家在解压中途关掉导入对话框，界面会冻结到当前步骤结束（`deployResources()` 落资源包、
`writeMetadata()` 写 JSON 都不检查 abort 位，只有解压的 progress 回调检查）。

**建议**：`abort()` 后把等待移出 UI 线程 —— 让任务对象改用 `QSharedPointer` 捕获自身，
析构只置位并 `deleteLater`；或至少在 `deployResources()/writeMetadata()` 的循环里加 abort 检查，
把冻结时间压到一次文件复制。
