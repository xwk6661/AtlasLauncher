# 07 · 一键汉化：可行性与方案

> ⏸ **本文描述的功能自 2026-11-12 起在界面上整体隐藏，代码保留。**
> 开关在 `launcher/maps/MapFeatures.h`（`maps::features::kLocalization`，当前 `false`）；
> 打开它，「信息 → 汉化」页签与「设置 → 地图 → 汉化翻译」分组就会回来，
> 实现与测试一直在编译、一直在跑。关闭原因见 [06 §63](06-变更记录.md)。
> 下面这些内容仍然有效——它是这个功能的完整设计与实测记录，恢复前先读一遍。

> 结论先行：**能做，且 Atlas 是这个功能唯一正确的落点**——但"一键汉化"必须重新定义。
> 它不是"点一下就全自动翻译并覆盖存档"，而是**一条可回滚的链路**：
> 体检 → 导出待译 → 取译文（机翻 / CSV 手填）→ 写回存档副本 → 逐区块结构比对 →
> **旧图打包备份、汉化版顶替同名世界目录**。
>
> **截至 2026-11-12 的状态**：这条链路（含 A 档重建 `resources.zip`）**全部落地**，
> 7 张真实地图的数字与参考实现对表通过（引用数逐位一致），C 档在 Torre de Piedra 上实测
> 结构差异 0、丢弃 0。实施记录见 §12、§13，逐条决策见 §11。
>
> 本文所有数字都是在**本机、真实地图**上跑出来的，不是引用交接包的样本值。
> 实测环境：Windows / Debug 便携数据目录 `build/win-local/Debug`。

## 0. 一句话

地图汉化**不是翻译问题，是三件事**：文本藏在哪里、哪些能翻、怎么改不坏。
`samples` 交接包把这三件事拆开并验证过；Atlas 缺的只是最后一段——**把它装进启动器，并补上
两条参考实现明确没做的路（1.8/1.12 老图、同图译版复用）**。

### 1.2 Atlas 已经有的地基（这是关键）

| 能力 | 现成组件 | 对本功能的意义 |
| --- | --- | --- |
| NBT 读写（含 gzip/zlib） | `libraries/libnbtplusplus`（`compound_tag` + `ozlibstream`/`izlibstream`） | 格式层最难的"读写对称、tag 类型不丢"白送 |

| 长任务 + 进度 + 取消 | `Task`、`InstanceTask`、`MapReinstallTask` | 汉化天然是长任务，宿主现成 |
| 存档内资源包落盘 | `MapImportTask::deployResources`（`saves/<world>/resources.zip` 随世界解开） | A 档产物直接有地方放 |
| 版本判定 | `MapVersionDetector` + `DataVersionTable` | 资源包 `pack_format`、`--quickPlay` 轨道都能算出来 |

**没有的**：MCA（`.mca` 扇区表）读写的 C++ 实现、文本分类规则、校验器。前者约 150 行，
后两者是纯逻辑，可照 `lang.py` 直译。

## 2. 本次实测（这一节是本文的骨架）

### 2.1 对 7 个真实实例 `probe`（只读，秒级）

```
Final Paradox      dv=2586 mode=key        ratio=0.988  refs=28747 lit=351 files=8444 res=Y
                                                       lang={'en_us':12879, 'es_*':12879×6}
Torre de Piedra    dv=3955 mode=injection  ratio=0.000  refs=0     lit=5   files=21   res=-
Ragecraft III      dv=0    mode=injection  ratio=0.000  refs=0     lit=0   files=0    res=-
Terra Restore      dv=1343 mode=injection  ratio=0.000  refs=0     lit=0   files=0    res=Y
Entropy            dv=1139 mode=injection  ratio=0.000  refs=0     lit=0   files=0    res=Y
盘灵古域            dv=0    mode=injection  ratio=0.000  refs=0     lit=0   files=0    res=-
Smaller CTM        dv=0    mode=injection  ratio=0.000  refs=0     lit=0   files=0    res=Y
```

结论：**7 张图里只有 1 张是 A 档（键化），其余 6 张全是要改存档的 C 档**，
而且这 6 张里有 5 张是 1.8.x–1.12 的老图。任何"只做 A 档"的方案，在这个库里等于没用。

### 2.2 A 档实测：Final Paradox 到底要翻多少

`export`（1.9 s）→ 11,815 条。但这是**未折叠**的数字。按 mcsl 自己的规则折叠
（打字机家族只留终点、碎片组只留一个代表）后：

| 指标 | 值 |
| --- | --- |
| 原始条目 | 11,815 |
| 折叠后翻译单元 | **5,767** |
| 再去重（同句只翻一次） | **5,688** |
| 总字符 | 278,073（≈ 7 万 token） |
| 含 `§` 格式码 | 3,462（61%） |
| 含私用区字形 | 0 |
| 别名：打字机家族 | 120 个（最大 109 键） |
| 分组：碎片多行组 | 462 条 |

这说明两件事：
1. **A 档地图的"一键"是算力问题，不是技术问题**——5,688 条 / 7 万 token，批量机翻完全跑得动；
2. **不做家族折叠就等于把工作量放大 2 倍**（11,815 vs 5,688），而参考实现的 `export`
   只标 `is_terminal`，不负责折叠。启动器这一层必须自己做折叠再送翻译。

### 2.3 C 档实测：参考实现有 3 个真实缺口

**(1) 告示牌全漏。** `inject.py` 的 `COMPONENT_KEYS` 只有小写 `text`，没有 `Text1..Text4`。
实测 Ragecraft III 单个 region 文件就有 **157 组** `Text1-4`（繁中版已全部译好，值是
`"加布里爾的強化背心"` 这样的 JSON 字符串）。也就是说 `analyze` 报的
`injection.translatable` **系统性低估了老图最大的载体**。

**(2) 碎片组没接到注入模式**（交接包自己的 D-001）。物品 lore 占 C 档文本大头，
不分组就是"英文语序的中文"。

**(3) "不支持 1.12 及更早"是过度保守**（D-004）。实测 1.8.9 的告示牌 `Text1-4`、
物品 `display.Name`、实体 `CustomName` **都是 JSON 文本组件或 JSON 字符串**，可以安全解析后改。
真正的裸字符串只有书的 `pages` 和 1.13 之前的命令方块——**这两类排除即可，不必整张图拒绝**。
直接证据：库里的繁中版就是这么做出来的。

### 2.4 新机制实测：同图译版"对齐复用"

拿 Ragecraft III 的英文原版（zip 内直接读）与繁中版（实例内）逐区块并行遍历，
只在**同一 NBT 路径**上两边都是字符串、且"原文无 CJK / 译文有 CJK"时记为一条译文：

```
elapsed 11.7s   chunk_ok=240  pair=222  not_en2zh=1   unique=37
```

样例（全部是人手译好的成品）：

| 路径 | 原文 | 繁中 |
| --- | --- | --- |
| `Level.TileEntities[1].SpawnData.id` | `Fire-Elemental` | `火元素` |
| `Level.TileEntities[2].SpawnData.id` | `Jungle Spider` | `雨林蜘蛛` |
| `Level.TileEntities[0].SpawnData.id` | `Rotten Explorer` | `腐敗探險者` |
| `Level.TileEntities[1].Items[4].display.Name` | `§8Secret Item` | `§8秘密物品` |
| `Level.TileEntities[1].Items[4].display.Lore` | `§f§oJokes so bad, your enemies will just fly` | `§f§o收藏來自各地最冷的笑話,絕對讓你沒朋友` |

**这条路的含义**：热门 CTM 图基本都有民间汉化版。只要玩家手里有"同图英文 + 同图汉化"，
启动器就能**差出一份高质量译表，一条都不需要机器翻**，再套简繁转换就是简体。
这是机翻永远比不上的质量，而且成本只是两次读盘。

风险：路径对齐依赖结构一致。实测 240 区块里 222 条命中、`chunk_missing=0`，
但两版差了几张 region 文件（繁中 56 / 英文 52）。所以必须加护栏：**列表长度不等就整段跳过**、
`count` 校验、译文长度比合理性检查，宁可少对不可错对。

### 2.5 性能实测：参考实现不能直接用

同一 region 文件（1024 区块）：

| 遍历方式 | 耗时 | 每区块 | 命中 |
| --- | --- | --- | --- |
| 全树遍历（参考实现的做法） | 10.81 s | 10.6 ms | 506 |
| **剪枝遍历**（跳过 `Sections`/`Heightmaps`/`Biomes`/`Data`/`BlockLight`…） | **1.58 s** | **1.5 ms** | **506** |

7 倍差距，命中数完全一致——慢在无脑遍历 4096 个方块状态数组。再叠加按 region 文件并行
（12 核机器，8 并发）：

- 56 个 region 文件 ≈ 57k 区块 → 顺序 **86 s** → 8 并发 **≈ 11 s**
- 对照：`analyze` 跑 Ragecraft III 实测 **> 11 分钟**（超时被杀），原因是全树遍历 + 串行

**结论：这个功能的性能上限由"剪枝 + 并行"决定，不由语言决定。** 原生 C++ 只是顺带更快。

## 3. 产品定义：交付什么

三条能力线，风险和体验完全不同，**必须分开呈现**，不能糊成一个"汉化"按钮：

| 线 | 做法 | 风险 | 产物 | 状态 |
| --- | --- | --- | --- | --- |
| **A · 键化**（资源包） | 只写 `zh_cn.json`，重建世界内 `resources.zip` | 零（写坏了最多显示回英文） | 世界内资源包 | ✅ 已实现（`applyToPack`，原包先备份） |
| **C · 注入**（改存档） | 复制存档 → 改 NBT 文本 → 结构比对 → 旧图备份后顶替 | 中（写错会毁档，所以有结构比对 + zip 备份） | 单实例内替换 | ✅ 已实现 |
| **对齐复用** | 同图两版差分取译文，再走 A 或 C | 低（不生产译文，只搬运） | 译文表 | ⬜ 未实现（可行性已验证，§2.4） |

> 命名说明：文档早期用过 A/B/C 三档（B = 注入、C = 对齐复用），后来代码与实测记录统一成
> **A = 键化、C = 注入**，对齐复用直接叫名字不占档位。本文与 `06` 的变更记录都按后者。

"初步"的定义（写进 UI 文案，别含糊）：

> 覆盖**玩家第一眼会看到的东西**——界面/物品名/实体名/告示牌/对话，
> 不保证书页排版、不保证图片化文字、不保证 100%。

## 4. 技术选型：不走 Python 子进程

交接包推荐"先 A（子进程）后 B（原生移植）"。**本项目应当直接跳到 B**，理由不是性能偏好：

| 方案 | 可行性 | 判决 |
| --- | --- | --- |
| A 子进程 + 随包便携 Python | 安装包 +10 MB；要处理 Python 缺失降级；两个进程的生命周期/超时/崩溃重建 | ❌ 为一个功能引入运行时依赖，且分发链多一层 |
| A' 子进程 + 检测系统 Python | 玩家机器大概率没有；装了也可能被商店版 python.exe 劫持 | ❌ 不可交付 |
| **B 原生 C++** | `libnbtplusplus` 已带 gzip 读写；libarchive 已在；缺的 MCA 约 150 行 | ✅ **采纳** |
| C 混合 | 两套代码边界难维护 | ❌ |

**但保留交接包的协议语义**：内部接口仍按 `probe/analyze/export/apply/verify` 五段划分，
字段名不变。好处是参考实现可以继续当"标准答案"跑回归——同一个地图，两边输出的
`key_ratio`、`translatable`、`structure_diffs` 必须一致。**这是移植期唯一可靠的验收手段。**

## 5. 架构

### 5.1 实际模块（都在 `launcher/maps/` 下，没有另开子目录）

早期计划里有一串细粒度模块（`McRegion` / `NbtTextWalker` / `TextClassify` / `LangTable` /
`MapL10nVerify` / `TranslationMemory` / `MapL10nDialog`）。实际写下来合并成了 5 个文件对，
因为那些"模块"之间的边界很虚——文本分类只有探针用，语言表读取只有导出用，
拆开只是多几个头文件。

| 模块 | 职责 | 行数 |
| --- | --- | --- |
| `MapL10nProbe.{h,cpp}` | `.mca` 扇区读、剪枝遍历、文本载体规则、散文判定、语言表读取、结构比对工具 | 1181 |
| `MapL10nTask.{h,cpp}` | 体检的 `Task` 宿主：线程池 + 进度 + 取消 | 160 |
| `MapL10nExport.{h,cpp}` | 产出 `strings.json` / `strings.csv` | 298 |
| `MapL10nTranslate.{h,cpp}` | OpenAI 兼容接口批量翻译 + 输出解析 | 430 |
| `MapL10nApply.{h,cpp}` | 写回存档副本、结构比对、备份打包、替换 | 1076 |
| `MapOptionsTxt.{h,cpp}` | 导入时写 `options.txt` 的语言与键位（不属于汉化，但同批做的） | 213 |
| `MapInstancePage.cpp` 的汉化页 | 四个按钮 + 三张卡片 + 弹窗流程 | ≈ 400 |

产品代码约 **3,750 行**，测试 **1,057 行**（4 个测试文件）。

**没有独立 `.mca` 写入模块**：写回是"读出扇区表 → 未改的按原始压缩字节搬运 → 改过的
重新序列化 → 重排扇区写整文件"，跟读取共用一个文件更不容易漂。这比原计划少一个模块。

### 5.2 数据流（实际）

```
实例「信息 → 汉化」页
      │
      ├── 快检（进页面自动跑，只读 datapacks + lang + resources.zip，<1 s）
      │      → 档位（完整 / 需改写存档）/ 键化率 / 载体三行
      │
      ├── 扫描全部区块（可选，串行；Final Paradox 691 MB 约 2 分钟）
      │      → 区块 / entities / data / 结构文件全部过一遍，线程池里跑，可取消
      │
      ├── 导出待译文本…  →  <实例>/l10n/strings.json + strings.csv
      │      判定：是散文 且 不含 CJK（否则中文原创图会把原文全导出来）
      │
      ├── 自动翻译…（可选）→  读 strings.json，分批送 LLM，译文写回同一文件
      │      没配 Key 也能走：Excel 改 csv 的 zh 列，导出时会合并回 json
      │
      ├── 生成汉化版（改存档）…  9 秒
      │      复制世界 → 改区块 NBT → 逐区块结构比对（不一致就丢弃该区块）
      │      → <实例>/.mcml-l10n/<时间戳>/MapWorld
      │
      └── 替换本实例存档  0.3 秒
             旧存档打包 → <实例>/l10n/backups/MapWorld-<时间戳>.zip
             旧目录改名挪开 → 汉化版就位 → 删掉临时目录
```

### 5.3 落盘布局（实际）

```
instances/<实例>/
├── .minecraft/saves/MapWorld/                 ← 当前在用的世界（可能是汉化版）
├── .mcml-l10n/<时间戳>/MapWorld/              ← 汉化版暂存（替换后移走，成功即消失）
└── l10n/
    ├── strings.json                           ← 待译/已译清单（自动翻译就地写回这里）
    ├── strings.csv                            ← 给 Excel 的表，UTF-8 带 BOM
    └── backups/MapWorld-<时间戳>.zip          ← 替换前的旧存档备份
```

没有 `l10n-report.json`：体检结果只留在内存里，切走页签就丢，重扫即可（成本可接受）。

## 6. 翻译层：三层设计，实际只落地了第三层

这一层交接包明确"不做"（ADR-007），理由是机翻术语错得离谱（`Blaze` → "火焰" 而不是"烈焰人"）。
**同意，所以不能只有机翻。** 但按优先级做完三层是三个迭代的事，当前只做了第三层（LLM），
第一层（对齐复用）的可行性已经实测过（§2.4），只是没接进产品。

### 6.1 第一层：对齐复用（⬜ 未实现，可行性已验证）

见 §2.4。补充判定：
- 只在同 `(文件, 区块, NBT 路径)` 上取对；
- 列表长度不等 → 整段放弃；
- 译文长度 / 原文长度超出 `[0.15, 3.0]` → 放弃；
- 同一原文对出多个不同译文 → 取众数，票数相同则放弃（保一致性）。

**为什么值得做**：库里 Ragecraft III 同时有英文原版和繁中版，240 个区块就抽出 222 对干净译文
（`Fire-Elemental→火元素`、`§8Secret Item→§8秘密物品`）。热门 CTM 图基本都有民间汉化，
**汉化不一定靠翻，靠对齐**，质量比任何机翻都高，成本只是两次读盘。

### 6.2 第二层：术语表（⬜ 未实现，部分以 prompt 硬约束代替）

来源两条：
1. **原版 `zh_cn.json`**（client jar / 资源索引里取）：`Blaze`/`Nether`/`Creeper` 这类原版术语
   直接查表。这不是"翻译"，是**查表**，零风险，也保证与原版游戏用词一致。
2. **对齐复用的产物**：Ragecraft III 的 222 对里已经包含 `Fire-Elemental→火元素`、
   `Jungle Spider→雨林蜘蛛`——这些是原作者/译者认可的名字，比任何机翻都权威。
   跑过几次就能积累成库里的 `l10n/glossary.json`。

**现状**：没有独立的术语表文件；LLM 的 system prompt 里硬编码了一小撮最常错的原版专名
（Creeper/Blaze/Enderman 等），够用但不系统。

### 6.3 第三层：LLM 批量（✅ 已实现）

`MapL10nTranslate` + `MapL10nTranslateTask`，入口是「汉化」页的 **自动翻译…**。

- 分批发送（按条数与字符数双阈值），批间串行，不并发也不限流；
- 强制回传 JSON，`§` 码、私用区字形、`%s` 占位符在 system prompt 里硬约束；
- 模型输出容错：容忍 ```json 围栏与前后客套话，缺字段/非法条目跳过（单测覆盖）；
- 某条没翻出来就**留空走原文**，宁可不翻也不写半句；中途失败时**已翻好的照样写回**；
- **没做的**：占位符丢失后的"回环校验 + 重译一次"——现在是信任模型输出，
  只在 prompt 里约束。这一条留给后续。

不做的事：不自动缩排（中文比英文宽，告示牌 90 px / 书页 114 px 会被裁），只报警。

## 7. 安全模型（哪一条破了都会毁档）

| 规则 | 落地方式 | 状态 |
| --- | --- | --- |
| 永不原地写 | `applyToCopy` 的目标存在就拒绝；源目录只读（单测用 SHA1 钉住） | ✅ |
| 改区块必比对 | 两边文本字段置空后逐区块比结构，不一致**丢弃该区块**并计数 | ✅ |
| 只改文本字段的值 | 解析 → 改值 → 重新序列化，绝不拼字符串 | ✅ |
| 字形不可翻 | 判定散文时先剔掉 `\uE000–\uF8FF` 私用区字形；LLM prompt 要求原样搬过去 | ✅ |
| 原子替换 | 写临时文件再 rename（`QSaveFile`）；备份 zip 落盘非空才动目录 | ✅ |
| 备份一次 | C 档先复制存档；替换前再把旧存档**打包成 zip** | ✅ |
| 家族只翻终点 | 打字机动画一帧一条，应只翻终点 | ⬜ 未做：导出没折叠家族，逐条都进清单，会白花翻译量 |
| 碎片组整组翻 | 被拆成多段的同一句话要整组送翻，否则中文语序会乱 | ⬜ 未做 |

后两条是"翻译质量"而非"毁档"问题：不做只是翻得更贵、语序更差，不会写坏东西。

**额外一条（Atlas 特有）**：地图自带的 `saves/<world>/resources.zip` 优先级高于玩家自选资源包。
所以 A 档**必须重建整包**（`build_full` 语义），不能只丢一个 `zh_cn.json` 的覆盖包——
否则地图的字体、贴图、`font/*.json` 全部丢失，字形图标会变成豆腐块。
交接包 §10.1 提到这点，但参考实现的 `apply` 默认走 `build_override`，**默认值是错的**。

### 11.1 顺带落地：导入时写 MC 默认配置（语言 + 键位）

做汉化就会碰到 `options.txt`——A 档资源包只有在游戏语言是中文时才有意义。
既然要在导入时写 `lang`，同一处就顺手解决了键位偏好。

**写法随版本分叉，这是这次最容易踩的坑**（依据是库里真实实例的 options.txt）：

| | ≤1.12（LWJGL2） | ≥1.13 |
| --- | --- | --- |
| 语言 | `lang:zh_CN` | `lang:zh_cn` |
| 蹲下 | `key_key.sneak:29` | `key_key.sneak:key.keyboard.left.control` |
| 奔跑 | `key_key.sprint:42` | `key_key.sprint:key.keyboard.left.shift` |

29 = `KEY_LCONTROL`、42 = `KEY_LSHIFT`。写错一代不是"没生效"——1.8 读到
`key.keyboard.*` 会当成未知键位丢掉，玩家的蹲/跑**静默回默认**。所以版本判不出来时
一律不写（`formatForVersion` 返回 `nullopt` → 跳过，而不是猜一个）。

**只在新建实例时写一次**。重装走 `reinstallWorlds`，不经过这段；进游戏后玩家怎么改都不会被覆盖。

实现：`launcher/maps/MapOptionsTxt.{h,cpp}`（纯函数，无 IO）+ `MapImportTask::applyOptionsDefaults`
（原来叫 `mergeOptionsTxt`，只写 `resourcePacks` 一行）。设置项 `MapOptionsForceChinese` /
`MapOptionsSwapSprintSneak`，默认都开，位置在 设置 → 地图 → 导入时的游戏设置。
测试 `tests/MapOptionsTxt_test.cpp`（12 组，含幂等与"保留无关行"）。

### 12.2 路上修正的四件事（都写进代码注释了）

1. **数据包里的 `.nbt` 结构文件不能漏**。Final Paradox 的 19 个结构文件里藏着 **716 处**
   translate 引用（占全图 2.5%）。第一版只扫 `.mcfunction`/`.json`，引用数直接少了 716。
2. **结构文件要按内容判，不能按键名判**。区块有稳定 schema（白名单更准更快），
   但结构文件里键名五花八门（1.8 的物品名在 `display.Name`），白名单必然漏。
3. **命令方块里不是 JSON 的 `{...}` 不算错误**。`{id:"minecraft:stone",Count:1b}` 是 SNBT
   的 NBT 前缀，Final Paradox 里有 62 处；第一版把它们计成"解析失败"，报告看起来像坏了。
4. **位置表越界的区块静默跳过**。地形生成中断的地图很常见，参考实现也这么做。

### 12.4 导出待译清单（已完成）

`launcher/maps/MapL10nExport.{h,cpp}`，入口是「汉化」页的 **导出待译文本…**，
产物落在 `<实例>/l10n/`：

- `strings.json` —— 结构化，字段 `kind/key/en/zh/count/referenced`，给后面的翻译与写回用；
- `strings.csv` —— UTF-8 **带 BOM**，Excel 直接打开填中文不乱码。

两条来源合并去重：资源包里"英文有、中文没有"的散文键（`kind=key`），
加上数据包与区块里的硬编码原文（`kind=literal`，按原文合并出现次数）。
`referenced` 标记这张图里是否真有地方引用该键 —— 没引用的多半是原版键，排序时沉底。

**判定规则里有一条必须写死：已经含中文的文本不算待译。** 库里好几张是中文原创地图
（Terra Restore 中文版、盘灵古域）或已汉化版本（Ragecraft III 繁中），
不排除的话清单里会全是地图自己的中文，玩家会以为装错了版本。
就是 `needsTranslation()`：是散文 **且** 不含 CJK。

实测（7 个真实实例，与 `probe` 同一次运行）：

| 实例 | 导出条数 | 资源包 | 存档 |
| --- | --- | --- | --- |
| Final Paradox | 11948 | 11618 | 330 |
| Ragecraft III（繁中） | 362 | 0 | 362 |
| 盘灵古域 | 334 | 0 | 334 |
| **Torre de Piedra** | **271** | 0 | **271** |
| Terra Restore（中文版） | 236 | 0 | 236 |
| Smaller CTM | 59 | 0 | 59 |
| Entropy | 24 | 0 | 24 |

**Torre de Piedra 的 271 条，与交接包验收清单里写的 `injection.translatable ≈ 271` 完全一致** ——
这条比引用总数更能说明实现是对的（它走的是"截取文本 → 散文判定 → 按原文去重"整条链）。
Final Paradox 的 11618 与参考实现的 11815 差 1.7%，差额来自我方更严的散文判定
（额外过滤了 base64 与全小写标识符），属于预期。
中文地图那几张（盘灵古域 4126→334、Terra Restore 937→236）掉的量，就是这条规则救回来的。

### 12.5 自动翻译（已完成，真实接口未实测）

`launcher/maps/MapL10nTranslate.{h,cpp}`，入口是「汉化」页的 **自动翻译…**，
设置里配 接口地址 / API Key / 模型（默认 `gpt-4o-mini`，任何 OpenAI 兼容网关都行）。

三个刻意的选择：

1. **不占线程**：全程 `QNetworkAccessManager` 异步回调，`executeTask()` 发完第一个请求就返回
   （教训见 06 §58.1：这个代码库里 `executeTask()` 只能派活）；
2. **批间串行**：一批回来再发下一批，不引入并发与限流问题；
3. **失败不写错**：某条没翻出来就留空走原文；中途失败时**已翻好的照样写回**。

system prompt 里的硬约束：保留 `§` 格式码与位置、私用区字形、`%s`/`%1$s` 占位符与 URL、
Minecraft 专名用官方译名。输出容错见 `parseResponse`（代码围栏、前后客套话、非法条目都有单测）。

**没实测的部分**：开发环境没有 key，真实接口一次都没跑过。已覆盖的只有"模型输出解析"。

### 12.6 C 档：写回存档副本（已完成）

`launcher/maps/MapL10nApply.{h,cpp}`，入口是「汉化」页的 **生成汉化版（改存档）…**。
流程：复制世界 → 在副本上替换文本 → 逐区块结构比对 → 写回；
产物在 `<实例>/.mcml-l10n/<时间戳>/MapWorld`，**源存档只读**（单测用 SHA1 钉住）。

抽取与写回共用同一份载体规则（`isTextKey` / `isTextListKey` / `isCommandKey` /
`isSkippedKey` / `isSkippedSubtree` 都在 `MapL10nProbe.h` 里公开）——
这样不会出现"抽得出的句子写不回去"。

实测（Torre de Piedra，1.21.1，67 MB，1.2 万个要扫的区块）：

| 指标 | 值 |
| --- | --- |
| 非空 region 文件 | 29 |
| 读到的区块 | 15731 |
| 改写的区块 | 64 |
| 替换的文本处数 | 804 |
| **结构差异** | **0** |
| **丢弃区块** | **0** |
| 耗时 | 9.0 秒 |

副本重新体检：区块数与原图一致，英文待译条数明显下降。

三条保守规则（都写在代码注释里）：

1. 未改动的区块**搬运原始压缩字节**，不"解压再压缩"；
2. 改过的区块先在**副本**上清空文本做结构比对，不一致就丢弃该区块、保留原文；
3. 位置表有异常、或单区块重新压缩后超过 255 扇区的，**整张文件保持原样**。

### 12.7 把副本变成可启动的世界

产物只是磁盘上的一个目录。收尾是 `replaceWorldWithBackup`（§13）：
旧存档打包成 zip → 汉化版顶替同名世界目录 → 启动游戏就是汉化版。
不建新实例、不删实例、不改 `map.json`。

## 13. 收尾：备份旧图 + 用汉化版顶替（已完成）

需求（2026-11-11 确认，末次修订：**不删实例**）：

1. 基于已经翻好的 `strings.json`，**一键导入**；
2. **旧存档打包成 zip 备份**，然后用汉化版**顶替同一个世界目录**；
3. 之后**启动的就是汉化后的那张图**（同名世界，实例与 `map.json` 都不用改）；
4. **没翻的条目保持原文**（不是留空、不是显示键名）。

最早的设计是"建汉化版副本实例 + 删原实例"，后来改成现在这样 ——
理由很实在：世界目录同名替换，`map.json`、版本、加载器、实例设置全都不用动，
风险面比"建新实例 + 删旧实例"小一个量级，而且旧存档有 zip 在手，随时能解压回去。

### 13.1 两条落地路径

| 档位 | 写哪儿 | 要不要副本 | 风险 |
| --- | --- | --- | --- |
| **A · 键化** | 重建世界内的 `resources.zip`，加 `assets/<ns>/lang/zh_cn.json` | **不需要**（原文没动） | 低，先备份 `.bak` |
| **C · 注入** | 改存档里的区块 NBT | 需要（先复制再改） | 中，必须结构比对通过 |

"没翻用原文"在两条路上都是自然结果：`zh` 为空的条目不写，原文原样留着。

注意 A 档必须**整包重建**（`build_full`），不能只丢一个覆盖包 —— 地图自带的
`resources.zip` 里还有字体、贴图与 `font/*.json`，覆盖掉会让图标变豆腐块（§7 已经写过一次）。

### 13.2 备份 + 替换的实现（`replaceWorldWithBackup`）

顺序是刻意排的，每一步失败都能退回去：

1. **校验汉化版完整**：必须有 `level.dat`。没有的话游戏会把它当新世界重建，
   玩家的存档等于"消失"（实际文件还在，但游戏里看不到原图）—— 直接拒绝；
2. **旧存档逐文件写进 zip**，用 `store` 不压缩。`.mca` 内部已经 zlib 压过，
   再 deflate 一遍只是白烧 CPU：实测 63.87 MiB / 76 个文件 **0.3 秒**，deflate 要几十秒；
3. **zip 落盘且非空**，才动目录：旧目录先改名挪到 `MapWorld.old-<时间戳>`，
   汉化版再改名就位；**就位失败就把旧目录改回来**；
4. 成功后才删掉那个临时挪开的旧目录（zip 里有完整备份）。

备份落在 `<实例>/l10n/backups/<世界名>-<时间戳>.zip`，同名不覆盖（自动加序号）。

### 13.3 界面

「生成汉化版（改存档）…」跑完后弹窗直接给三个选择：

- **替换本实例存档**（默认）
- 打开目录
- 稍后

选替换会再确认一次（列出备份目录），并且**游戏运行中直接拒绝** ——
`session.lock` 与 region 文件被占用时挪不动，硬来还可能把正在保存的世界写坏。

替换成功后清空过期的体检结果（导出/翻译/生成都基于旧存档），
页面上留一行提示备份位置。想回到原图：把 zip 解压回 `saves/`，或用「重装地图」从地图库还原。
