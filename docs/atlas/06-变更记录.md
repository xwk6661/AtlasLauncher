### 1.1 十条最贵的教训

| 教训 | 出处 |
| --- | --- |
| **先做对照实验，再改代码**：同样的症状换个启动器/断开远控是否复现，比读上游工单快得多 | §17 |
| **症状对上号 ≠ 原因对上号**：引用了真实存在的 Mojira 工单，也可能完全不是这次的原因 | §17、§47 |

| **上游的 override 设置读不到实例值**：`JvmArgs` 在 `OverrideJavaArgs=false` 时永远回落到全局 | §18 |
| **中文 Windows 的编码/路径是雷区**：GBK 日志路径、`QLatin1String` 解 UTF-8、CSV 的 BOM 字节 | §18、§50、§57 |
| **界面先于能力就是负资产**：功能不完善时，界面越完整，玩家越容易点进去看到一堆数字 | §63 |

## 4. 专题 · 大厅封面通道（2026-11-02）

**根因**：`*.supabase.co` 是按 SNI 阻断（DNS 正常、TCP 通、TLS 收不到 ServerHello）；Qt 在 Windows 走 Schannel，
不支持 ECH，补 UA/Referer 也没用。决定性对照：同一 URL 用 Edge 无头 `<img>` 3.3s 正常出图。

**方案 `MapCoverLoader`**（列表 / 详情 / 大厅 / 信息页共用）：内存 LRU 96 + 磁盘 `<数据目录>/maps/covers/<sha1>.jpg`；
先 Qt 直连，失败把 host 标记为 Browser，之后同类直接走浏览器；一个进程批量取 8 张、页内并发 6，
`<img> → canvas 480px → toDataURL(jpeg, 0.82)` 后从 `--dump-dom` 收回；**必须 `--disable-web-security`**
（跨域图 tainted，`toDataURL` 直接抛异常），一次性 profile 用完即删；失败两次才记 bad。

**边界**：`ctmrepository.com` 的 50 张仍取不到（Cloudflare 不认无头浏览器）；首次 20 行约 12s，之后磁盘命中。

## 5. 专题 · 「更新数据」误报「浏览器进程崩溃 62097」（2026-11-02）

**现象**：点「更新数据」报"浏览器进程崩溃（退出码 62097）"，但直接打开大厅一切正常 —— 因为打开只读本地快照。

**根因**：同一条 REST URL 约 1/3 概率被 RST（与响应体大小无关）；旧实现一跳一进程，撞上就杀进程，
把"被杀"报成了"崩溃"（62097 只在强杀时出现）。

**修法 `BrowserFetch`**：打开本地页面、页内 `XMLHttpRequest` + 退避重试 3 次（300/600ms）、base64 回传；
能拿到真实状态码（4xx 直接失败并带服务端 message，5xx/重置才重试）；超时 30 → 60s，`--virtual-time-budget` 25s。
**不能加 `?_r=N`**：PostgREST 对未知参数直接 `PGRST100`（400），重试会全灭。

## 12. 专题 · 启动失败导致启动器退出（2026-11-03 上午）

点「启动」游戏窗口不出现、启动器自己关掉，日志停在 `ASSERT "(!isRunning()) == false"`。
四个独立问题叠在一起（逐条见结论表 #59–#62），核心教训是：**Debug 下的断言 `qFatal` 会把"一次启动失败"升级成"整个启动器退出"**，
以及**冷启动时 `traits()` 是空的，不能据此判轨道**。

**已知代价**：traits 未知这个窗口里不注入 Agent，所以"启动器刚打开就点启动"时 ≤1.19.4 可能停主菜单（彻底修在 §47）。

| # | 问题 | 根因 | 修法 |
| --- | --- | --- | --- |
| 59 | **Java 检查被 15s 超时杀掉，判定成"起不了 java"** | `JavaChecker` 用 `javaw` 跑 `JavaCheck.jar`；首次在新路径执行时进程报完三个属性后不退出（扫描/挂起），15s 后被 `kill()` → `CrashExit` → `CheckJava` 直接失败。手动跑同一个 jar 只要 0.46s | `finished()` 里区分「被超时杀掉但 stdout 已有 `java.version`」→ 按有效结果继续，只记一条警告；`ExitCode==1` 仍判失败 |

## 17. 专题 · 第二次启动失效 + 视角乱转（2026-11-03 下午，第二轮）

### 17.1 看门狗连到了**上一次**的 LaunchTask（#63）

`LaunchTask::create()` 里 `init()` 先 `setRunning(true)` 发 `runningStatusChanged(true)`，
之后 `LaunchController` 才把新对象写进 `m_launchProcess`。所以信号到达时 `getLaunchTask()` 拿到的是
**上一次那个已结束的任务**（第一次启动是 `nullptr`，靠重试躲过去了）—— 连上的是死对象，所以第二次永远收不到日志。

修法：不依赖信号，加 300ms 定时器比对 `getLaunchTask()` 与 `QPointer<LaunchTask> m_hookedTask`，
不一致就断开重连；任务销毁时 `QPointer` 自动变空也会重连。

### 17.2 视角锁死/狂转：**误判**，真因是远控软件（#64）

当时按 Mojira MCL-24083（quickPlay 无焦点抓不住鼠标）推理，新增 `MapWindowFocus`：启动后每 250ms 找该进程的
GLFW 窗口把前台交过去，只在本进程仍占前台时动手，盯满 30 秒且连续 3 秒是前台才收工。

真机结论：**是 ToDesk / 向日葵**，断开远控即恢复，与启动器无关。判断失误在于"同一个症状直接归给最像的已知缺陷"，
没先做"换官方启动器 / 断开环境工具"的对照。`MapWindowFocus` 保留（对应真实缺陷，且不改变正常行为），
但它**没有**修好这次的问题。

## 26. 下载源：可选 BMCLAPI 镜像（2026-11-04）

## 27. 下载源这一页：中文说明、顺序、连通性测试（2026-11-04）

下载源挪到页面顶部并写中文说明（**只影响文件下载**、**镜像请求不走代理**）；镜像模式下「资源服务器」禁用
（`AssetUpdateTask::resourceUrl()` 直接返回官方值，留着可编辑只会造成"设了镜像还在打自定义地址"的错觉），
但元数据服务器 / 旧版 FML 库 / Pastebin / UA 不受影响，不一刀切锁死。

「测试连通性…」逐条请求四个**真实文件**并显示实际会打的地址，一条失败就停。两个实现坑：
1. 要用**未保存**的下拉值 → `rewriteFor(url, bool)` + 请求带 `Option::NoSourceRewrite`，

## 29. 真实下载的镜像换节点重试（2026-11-04）

**先证明重试安全**：`FileSink` 写的是 `QSaveFile`（临时文件 + `commit()` 才改名），重入 `init()` 等于从零写，
`abort()` 会删临时文件、目标位置原有的好文件还在。现在改成显式 `cancelWriting()` + `reset()`，并用三个用例钉住。

**重试规则**：回到**镜像入口**重试（302 之后 `m_url` 已是节点域名，接着打同一节点等于确定性失败）；最多 3 次
（单次 40% 时 4 次后失败率约 13%）；只认**连接层**错误（4xx/5xx 就停手 —— 换节点不会把 404 变 200）；只重试 GET；
重试前 `sink->abort()` 丢半截并作废哈希；用 `QTimer` 退避而不是在 `finished` 槽里立刻重发（不能在自己的信号里析构 reply）；
官方源**一个字节都不动**（没有 `m_mirrorBaseUrl` 就永不重试）；新增 `Option::NoMirrorRetry` 给连通性测试用（否则"每条 5 次"叠成 20 次）。

与 `NetJob` 的任务级重试是两层：这层管"一个节点抖一下别把整个任务打挂"，那层管"整轮重来"。
代价是最坏 4×3 次，所以只对镜像开。

顺带：`Request` 里三处 `APPLICATION->` 改 `APPLICATION_DYN`，否则单测里 `qApp` 是普通 `QCoreApplication`，`static_cast` 出来的指针一取 settings 就崩。

## 32. 大文件分片下载：做成可配置项（2026-11-04）

补 §31 的盲区：只剩最后一个大文件时，池也只能给它一条连接（30–60 KB/s）。

段数不超过字节数，否则出现 0 长分片、Range 直接 416。

**关键坑**：决定拆段时必须丢掉那条没带 Range 的响应，否则它会把整个文件拉回来覆盖别的分片；

服务器回 200 而不是 206 就整体降级单连接。

实测 24 MB：单连接 237 秒 / 98 KB/s → 8 段 7.0 秒 / 3324 KB/s，sha1 与官方一致。

## 33. 分片下载真的跑起来了：三个 bug（2026-11-05）

§32 上线后用户实测 28 MB 的 `client.jar` 仍只有 368 KB/s、5 秒后两片报错、10 秒整体降级。三个只有真跑才现形的问题：

   必须 `release` + `abort` + `deleteLater`，把析构交给事件循环。

实测用户失败的那个 jar（29.5 MB）：9.6 秒 / 2998 KB/s / sha1 一致。

## 36. 卡 29 分钟的根因：重试从第 0 字节重来（2026-11-05）

19.5 MB 的 `client.jar` 从 1089 秒卡到 2829 秒、6 次尝试全失败，每次从 0 开始。

于是永远在完成前被掐，重试再从头就永远完不成。

修：顺序下载写 `<目标>.part`（`QSaveFile` 的隐藏临时文件一 `abort()` 就没了，没法续传）+ `init()` 发现 `.part`
