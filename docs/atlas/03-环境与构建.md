## 3. 五个环境坑（都已解决，按这个来）

| # | 坑 | 现象 | 解法 |
| --- | --- | --- | --- |
| 1 | vcpkg 的 git 注册表要完整历史 | 浅克隆 `microsoft/vcpkg` 到 63 MB 停滞 | 把本地浅克隆当 **builtin 注册表**：manifest 加 `builtin-baseline`，`vcpkg-configuration.json` 用 `{"kind":"builtin","baseline":…}` |
| 2 | vcpkg 要 pwsh 7.6.9 | 卡在下载 `PowerShell-7.6.9-win-x64.zip`（109 MB） | 16 线程分段下载 → 校验 SHA512 → 放进 `vcpkg/downloads/`；lzo / bzip2 同理从清华镜像取（哈希一致即可） |
| 3 | **VS 实例没注册 Windows SDK** | 端口构建报 `rc` 找不到、`LNK1104: kernel32.lib` | overlay triplet + `VCPKG_ENV_PASSTHROUGH RC LIB INCLUDE PATH`（见下） |
| 4 | 上游 Java 子项目用 `-source 7` | `错误: 不再支持源选项 7` | 预设里把 `JAVAC/JAR/JAVA_EXECUTABLE` 指向 JDK 8 |
| 5 | **`Qt6Core.dll` 被复制到 exe 旁边后找不到平台插件** | 启动即弹 `no Qt platform plugin could be initialized` | `run-atlas-debug.cmd` 每次启动写 `qt.conf`（`Prefix=<Qt 根>`）并设 `QT_PLUGIN_PATH` |

**坑 3 的关键**：vcpkg 给端口构建的是**干净环境**，进程内改 `PATH`/`RC` 传不进去；而本机
`Enter-VsDevShell` 之后 `WindowsSdkDir` 是空的。所以用本地 overlay triplet：

```cmake
# E:/Program File/vcpkg-manifests/prism/triplets/x64-windows.cmake（不进仓库）
include("<仓库根>/cmake/vcpkg-triplets/x64-windows.cmake")
set(VCPKG_ENV_PASSTHROUGH RC LIB INCLUDE PATH)
```

**⚠ ABI 哈希**：`RC` / `LIB` / `INCLUDE` / `PATH` 都参与 vcpkg 的 ABI 哈希。
`run-vcpkg.ps1` 与 `run-configure.ps1` 必须 dot-source **同一份** `env-toolchain.ps1`，
否则每换一次环境就把 18 个依赖重编一遍（11–20 分钟）。

**坑 5 的机理**（2026-11-10 踩到）：`run-atlas-debug.cmd` 为了让提权的 `atlas_filelink.exe`
也能加载 Qt，会把 `Qt6Core.dll` / `Qt6Network.dll` 复制到 `build/win-local/Debug/`；
Windows 先搜 exe 目录，于是 `atlas.exe` 用的是这份本地副本。Qt 6 按 DLL 位置反推 prefix，
而 `Debug\` 不在 `<prefix>\bin` 下 → 插件目录算成空，只剩 `Debug\platforms`（不存在）。
判据是 `QT_DEBUG_PLUGINS=1` 下的 `Could not find the Qt platform plugin "windows" in ""`。
脚本现在每次启动重写 `Debug\qt.conf`（`[Paths] Prefix=…`），换 Qt 只改脚本里的 `QT_BIN`；
**脚本注释必须保持 ASCII**——cmd 按 OEM 代码页读文件，UTF-8 中文会被当命令执行。

## 4. 沙箱 / 自动化环境下的临时配方

在受控沙箱里跑 `cmake --preset` 会触发 vcpkg 重装依赖，而安全策略**拦掉了 `reg.exe`**：

1. `vcvars64` / `Enter-VsDevShell` 静默失败 → 只设了 MSVC 的 `INCLUDE`/`LIB`，**没有 Windows SDK 路径**；
2. cmark 的 try-compile 依次挂在 `rc` 和 `kernel32.lib` 上，vcpkg 顺手把 `vcpkg_installed` 清空；
3. 于是整棵工程不可编译。

临时解法：`build/_build_env.cmd` 手工写全 `INCLUDE`/`LIB`/`PATH`（**SDK 在前、MSVC 在后**）再 `cmake --preset`，
可稳定出包。代价是 ABI 哈希与 `env-toolchain.ps1` 不一致 —— **接手后先跑一次 `build/run-vcpkg.ps1` 归一**，
之后照 §2 走，否则每次都会全量重编。

另一个反复出现的干扰：链接大文件（`LauncherTests.exe` 28 MB / `.pdb` 280 MB）时偶发
`C1083: Permission denied` 或链接挂起十几分钟，重跑即可，**不是代码问题**。
`C1083` 也可能出现在编译阶段（报"无法打开编译器生成的文件 … .obj"）：同样的源码单独编能过、
下一次重跑也能过，属于写 `.obj` 时的瞬时占用，不是 ACL 或磁盘问题。
**并行度越高越容易撞上**：连着几次失败时，`$env:CMAKE_BUILD_PARALLEL_LEVEL="3"` 再跑一次基本必过。

### 4.1 沙箱里 vcpkg 端口构建会卡死（2026-11-03 实测）

在受管沙箱内跑 `cmake --preset` 时，用 **CMake** 构建的端口（cmark / ecm / zstd / libarchive…）正常，
但用 **autotools** 的端口（`lzo` 等）会停在 `-- Configuring x64-windows` 不动：
`configure` 依赖 vcpkg 自带的 msys2 环境，沙箱会拦掉其中的子进程（同一次运行里还能看到
`reg.exe` 被 Program Blacklist 拒绝）。现象是 `cl.exe` 常驻 0 CPU、`config-*-out.log` 一直为空。

解法：把 `cmake --preset` / `cmake --build` 放到沙箱外跑一次（本机实测 15 个包 10 分钟装完，
其中 `lzo` 只需几秒）。**不要**因为卡住就判定"依赖装坏了"。

**2026-11-15 补充**：`build/run-configure.ps1` 本身也会被拦 —— 它 `Enter-VsDevShell` 时拉起
`reg.exe`，直接命中 Program Blacklist，命令在"什么都没干"的状态下失败。绕过办法是**跳过 VS 环境脚本**，
手抄 `build/env-toolchain.ps1` 里那四个变量再调 cmake（路径按本机实际值改）：

```powershell
$sdk = "C:\Program Files (x86)\Windows Kits\10"; $ver = "10.0.26100.0"
$vc  = "D:\Program Files\Microsoft Visual Studio\2022\VC\Tools\MSVC\14.44.35207"
$env:RC = "$sdk\bin\$ver\x64\rc.exe"
$env:INCLUDE = "$sdk\Include\$ver\ucrt;$sdk\Include\$ver\um;$sdk\Include\$ver\shared;$sdk\Include\$ver\winrt;$vc\include"
$env:LIB = "$sdk\Lib\$ver\ucrt\x64;$sdk\Lib\$ver\um\x64;$vc\lib\x64"
# PATH 必须与 env-toolchain.ps1 逐字一致：它参与 vcpkg 的 ABI 哈希
$machine = [Environment]::GetEnvironmentVariable('PATH','Machine')
$user    = [Environment]::GetEnvironmentVariable('PATH','User')
$env:PATH = "$sdk\bin\$ver\x64;$vc\bin\Hostx64\x64;$machine;$user"
& "D:\Program Files\Microsoft Visual Studio\2022\Common7\IDE\CommonExtensions\Microsoft\CMake\CMake\bin\cmake.exe" --build --preset win-local
```

> **PATH 别随手拼**：`RC` / `LIB` / `INCLUDE` / `PATH` 都是 vcpkg 的 passthrough 变量，进 ABI 哈希。
> 2026-11-15 用"当前 PATH 后面接 SDK"跑过一次，哈希变了 → 6 个依赖重编（8 分钟）；
> 换回上面这条从注册表重建的 PATH 后立刻恢复 `already installed`。

## 6. 产物与数据目录（便携模式）

`build\win-local\Debug\` 同时是**运行数据目录**：exe 旁有 `portable.txt`，所以
`atlas.cfg`（改名前的 `prismlauncher.cfg` 已复制过来，原文件保留作备份）、
`instances\`、`maps\`（库 + 大厅缓存 + 封面缓存）、`accounts.json` 都在这里。

**不要对 `build` 目录做 clean** —— 那会连玩家数据一起删掉。

### 6.1 资源库包含什么（不是只有 `assets/`）

| 位置 | 内容 | 本机体积 | 缺了会怎样 | 判定依据 |
| --- | --- | --- | --- | --- |
| `assets/objects/` | 素材本体，按 sha1 平铺成 `<前两位>/<hash>` | 1.8 GiB（12,625 个） | 重下 | **文件在 + 大小一致**（`AssetObject::getDownloadAction`） |
| `assets/indexes/` | 每版的素材清单 json | 10 MB（34 份） | 重下（启动时本来就会条件请求刷新） | metacache + ETag |
| `libraries/` | 库 jar，以及**每版 client jar**（`com/mojang/minecraft/<ver>/`） | 2.1 GB（**103 个**版本的 client jar 已落盘） | 重下 | **metacache** |
| `java/` | 解压好的 Mojang 运行时 | 270 MB | 重下（`AutoInstallJava`） | 目录存在 |
| `meta/` | 版本 json、加载器元数据 | 6 MB（125 个） | 重下 | metacache |
| `metacache` | **一本账**：哪些库文件已经下过（记路径 + md5 + 时间戳） | 301 KiB（789 条） | `libraries/` **整份重下** | — |

> 2026-11-14 起本机这三份资源（assets / libraries / java）在 `D:\Games\Minecraft\PrismLauncher`
> （`SharedResourceDir`），上表体积仍是它们的实际大小，只是不再占数据目录。

三条容易踩的规则：

1. **素材不需要账本**：`assets/objects` 的判定是"文件在、大小对"，直接把目录拷过去就认。
2. **库文件认账本，但账本缺失可以补**：`Library::getDownloads()` → `HttpMetaCache::resolveEntry()`，
   条目缺失时会先按版本元数据里的 sha1 核对本地文件，对得上就补记录、跳过下载（2026-11-14 起），
   对不上才重下。所以 `metacache` 没跟过来不再等于"整份重下"，只是要多读一遍文件。
3. **账本不怕改路径/改时间戳**：条目里存的是相对路径 + md5，base 路径启动时按设置重算；
   复制后 mtime 变了也没关系 —— 会重算 md5 比对，一致就继续认账。

### 6.2 三种"换库"的做法

| 想做的事 | 正确做法 |
| --- | --- |
| 挪到别的盘 | **设置 → 资源** → 选目录 → **应用资源库**（搬 `assets`/`libraries`/`java`；`meta` 与 `metacache` 留在数据目录，它们按数据目录解析）→ **立即生效，不用重启**（2026-11-14 起会把 metacache 基址一起改过去，见 [06 §70](06-变更记录.md)） |
| 整份拷给别的机器 | 复制 `assets/` + `libraries/` + `meta/` + `metacache` 四项，`java/` 可选（不拷＝重下约 500 MB）。只拷 `libraries/` 不带账本也能用：首次用到时会按 sha1 认领，不重下（要读一遍文件） |
| 清空重下 | 删 `assets/objects`（想连库一起重下就再删 `libraries/`）。`metacache` 可留 —— 留着只是省不下，删了也只是多下一次 |

**别做的事**：把 `meta/`、`metacache` 塞进共享资源目录（它们按数据目录解析，塞过去等于没生效）。
只拷 `libraries/` 不带 `metacache` 已经不算忌讳了（2026-11-14 起会认领），只是第一次要多读一遍文件。

**拿别人的库来用**（官方启动器的 `%APPDATA%\.minecraft`、另一台机器的 Prism 目录）：

- `assets/objects` ✅ 认（按 hash 命名 + 大小一致）；
- `libraries/` ✅ **认领**（2026-11-14 起）：账本里没有、但文件在，就按版本元数据里的 sha1 核对内容，
  对得上直接补账本并跳过下载；对不上才重下。所以「扫到」现在等于「能用」，代价是首次读一遍文件。
  「设置 → 资源 → 检测已有目录」会把这些位置扫出来。

## 8. 仓库外动过什么（可撤销）

| 位置 | 改了什么 | 为什么 |
| --- | --- | --- |
| `…vcpkg-manifests/prism/vcpkg.json` | 加 `builtin-baseline` | 坑 1 |
| `…prism/vcpkg-configuration.json` | `builtin` 注册表 + 本地 overlay triplet | 坑 1 |
| `…prism/triplets/x64-windows.cmake` | 新增，透传 RC/LIB/INCLUDE/PATH | 坑 3 |
| `E:/Program File/vcpkg/downloads/` | 手工放入 pwsh / lzo / bzip2 源码包 | 坑 2 |
| `CMakeUserPresets.json`（gitignore） | ninja / rc / cl / JDK8 的绝对路径 | 坑 3、4 |
| `build/*.ps1`、`run-atlas-debug.cmd`、`_build_env.cmd` | 一键复现 | — |

> **仓库目录改过名（`PrismLauncher` → `Atlas` → `AtlasLauncher`）时，仓库外这几处必须同步改**，
> 否则 configure 会挂在 `Overlay path … must be an existing directory` 或
> `include could not find requested file: …/cmake/vcpkg-triplets/x64-windows.cmake`：
> `…prism/vcpkg-configuration.json` 的 `overlay-ports` / `overlay-triplets`、
> `…prism/triplets/x64-windows.cmake` 里的 `include(...)`。仓库内的 `build/*.ps1` 已改为按
> `$PSScriptRoot` 推导，不用再改。CMake 还会把旧源码路径写进 `build/win-local/CMakeCache.txt`
> 与 `CMakeFiles/impl-*.ninja`，改名后必须重新 configure（见 [06](06-变更记录.md) §11）。

**没有**改注册表或系统环境变量。
