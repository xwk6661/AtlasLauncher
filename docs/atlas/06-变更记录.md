## 4. 专题 · 大厅封面通道（2026-11-02）

**现象**：列表和详情只有本地生成的占位封面（标题哈希色块 + 首字母），一张真图都出不来。

**根因（先排除掉的错误猜测）**：

- 封面地址并不都在同一台机器上：缓存里 **874/1000** 在
  `https://qtxjbukjyuylqjgiphxs.supabase.co/storage/v1/object/public/map_images/…`，
  50 张在 `ctmrepository.com/map_img/…`，75 张没有封面字段。
- 对 `*.supabase.co` 实测：DNS 正常（Cloudflare `104.18.38.10` / `172.64.149.246`），
  TCP 能连上，但 **TLS 握手收不到 ServerHello**（`curl: (35) schannel: failed to receive handshake`）。
  这是**按 SNI 的阻断**，不是超时、不是证书、也不是代理没配。
- 本机 Qt 在 Windows 走 Schannel，**不支持 ECH**，所以 Qt 网络栈无论怎么调代理都过不去
  （这也解释了为什么上一轮把 UA/Referer 都补上了仍然 0% 命中）。
- 决定性对照实验：同一个 URL 用 Edge 无头模式的 `<img>` 打开，**1920×1080 / 3.3s 正常出图**。
  Chromium 支持 ECH，这是本机唯一能过的通道。

**方案**：`maps/MapCoverLoader`（列表、详情、大厅对话框、实例信息页共用）

1. 内存 LRU（96 张）+ 磁盘缓存 `<数据目录>/maps/covers/<sha1(url)>.jpg`，命中就完全不出网；
2. 先 Qt 直连（有代理/没被阻断时最快），失败后把这个 **host 标记成 Browser**，之后同类请求直接走浏览器；
3. 浏览器通道：**一个进程批量取 8 张**，页面内并发 6；
   `<img>` → canvas 缩到 480px → `toDataURL('image/jpeg', 0.82)` → 写进 `<pre>`，
   宿主从 `--dump-dom` 的输出里把 base64 收回来解码落盘。实测 6 张 4.1s、单张 4.6s（含进程启动）；
4. 必须带 `--disable-web-security`：跨域图片画进 canvas 会被标记为 tainted，`toDataURL` 直接抛异常。
   进程用一次性空白 profile、只加载我们自己生成的临时页面，跑完即杀并删除目录；
5. 失败两次才记 bad，避免一次网络抖动就永久放弃某张图。

**验证**：`test_coverLoaderBrowser`（需 `PRISM_TEST_COVER_URL`，默认 skip）：
生成页面 → 起浏览器 → 收回 JPEG → 落盘 → 二次请求命中缓存，全部 PASS。

**已知边界**：`ctmrepository.com` 的 50 张仍取不到（Cloudflare 不认无头浏览器）；
首次打开大厅 20 行约 3 批 ≈ 12s 才陆续出图，之后磁盘命中；不建议预热全部 1000 张。

## 5. 专题 · 「更新数据」误报「浏览器进程崩溃 62097」（2026-11-02）

**现象**：大厅打开一切正常（封面、简介、评论都在），唯独点「更新数据」弹错误面板，
技术细节是 `…/rest/v1/maps?select=…&limit=1000`，原因写「浏览器进程崩溃（退出码 62097）」。

**为什么"直接打开"没事**：大厅页打开时**只读本地快照**（`<数据目录>/maps/hall-cache.json`），
一个请求都不发；「更新数据」才会真的出网做 4 个请求。两条路径完全不同。

**排查**：

1. 用应用的同一组参数重放那条 REST URL → `net::ERR_CONNECTION_RESET`，3 次里 2 次失败；
   换 `limit=5` 同样概率 → **与响应体大小无关，这条链路本身约 1/3 概率被 RST**；
2. 并发 3 个无头实例（2 图 + 1 JSON）→ 全部正常退出，排除"多个浏览器打架"；
3. 退出码 62097 只在进程被**强行终止**时出现，不是服务端错误；
4. 旧实现是"一次进程只发一跳"，撞上 RST 或超时就杀进程重开，第 4 次仍失败，
   最后把"被杀"报成了"崩溃"。

**修复**（`BrowserFetch`，所有浏览器通道请求一起受益）：

- 浏览器改为打开**本地页面**，页面里用 `XMLHttpRequest` 取目标 URL，**页面内退避重试 3 次**（300/600ms），
  响应体 base64 回传；
- 能拿到真实 HTTP 状态码：4xx 直接失败并带出服务端 `message`，5xx / 连接重置才重试；
- 进程超时 30s → 60s，`--virtual-time-budget` 25s（够 2.5 MB 响应体）；
- **不能**加 `?_r=N` 之类的防缓存参数：PostgREST 对未知查询参数直接 `PGRST100`（400）。

**验证**：`test_browserChannelJson`（`PRISM_TEST_FETCH_URL`，默认 skip）——
小响应 3.8s、真实 1000 行详情响应 2.6s，均 PASS。

## 9. 专题 · 资源库可迁移（2026-11-02 晚）

**问题**：首次进图时那一串 `piston-data.mojang.com/v1/objects/…/jvm.dll` 下载的是
**Mojang 官方 Java 运行时**（400 多个文件），连同 `assets`、`libraries` 都在数据目录里——
在 C 盘既占系统盘，换一个启动器还要整份重下。

**修复**：

- `launcher/ResourcePaths`：`assetsDir / librariesDir / javaDir` 统一算绝对路径，
  设了共享目录就用 `<共享>/assets|libraries|java`，否则仍是数据目录（默认行为不变）。
  替换掉 7 处写死相对路径（meta cache 两个 base、`AssetsUtils` 两处、`AssetUpdateTask` 读索引、
  `MinecraftInstance` 的库路径与 `assets_root`、`Application::javaPath`）。
- 全局设置 **「资源」页**（「游戏」右边）+ `maps::ResourceStore`：选目录、**检测本机已有资源**
  （当前数据目录 / `%APPDATA%\.minecraft` / 其他 Prism/MultiMC）、一键**迁移**。
- 同盘直接 `rename`（瞬间完成），跨盘逐个复制、成功后删源；不勾迁移则只切路径。
- **没有用目录联接（junction）**：迁移后就是普通目录，备份/换机器/给别的启动器复用都不依赖 reparse point。
  代价是改完要重启启动器（assets/libraries 的绝对路径在启动时就进了 meta cache）。

**为什么放弃联接**：`mklink` 要经过一层命令行解析与引号规则（路径带空格很容易写坏），
reparse point 出问题时又只报「文件名或目录名语法不正确」这类无上下文错误；
既然本来就允许搬文件，直接改路径解析更干净（也顺带修掉了 `QDir("libraries")` 这类隐式依赖 cwd 的写法）。

## 12. 专题 · 启动失败导致启动器退出（2026-11-03 上午）

**现象**（用户实测）：点「启动」后**游戏窗口不出现**，反而**启动器窗口自己关掉**。

| # | 问题 | 根因 | 修法 |
| --- | --- | --- | --- |
| 59 | **Java 检查被 15s 超时杀掉，判定成"起不了 java"** | `JavaChecker` 用 `javaw` 跑 `JavaCheck.jar`；首次在新路径执行时进程报完三个属性后不退出（扫描/挂起），15s 后被 `kill()` → `CrashExit` → `CheckJava` 直接失败。手动跑同一个 jar 只要 0.46s | `finished()` 里区分「被超时杀掉但 stdout 已有 `java.version`」→ 按有效结果继续，只记一条警告；`ExitCode==1` 仍判失败 |

| 61 | **`--launch` 在启动瞬间崩** | `INISettingsObject::suspendSave()` 用 `bool` + `Q_ASSERT(!m_suspendSave)`，而 `SettingsObject::Lock` 是 RAII，嵌套加锁是合法用法 | `m_suspendSave` 改成计数器，`resumeSave()` 到 0 才落盘 |
| 62 | **修好 java 后仍停在主菜单** | `MapLaunchPrep` 在 `Application::launch()` 里读 `instance->traits()`，那一刻组件还没解析 → traits 为空 → 1.21.1 被判成「不支持 quickPlay」→ 走 Agent 轨道（1.21.1 恰好有符号表）→ 顺手把 `JoinWorldOnLaunch` 清空 → 游戏停主菜单 | traits 为空时**不判轨道**：只写世界名（`processMinecraftArgs` 里已解析完，会按 trait 自己决定），不注入 Agent，并打印 `traits unknown` 警告 |

## 17. 专题 · 第二次启动失效 + 视角乱转（2026-11-03 下午，第二轮）

上一轮的两个修复都没生效，重新查了一遍，根因都跟第一轮的判断不一样。

### 63. 看门狗连到了**上一次**的 LaunchTask（不是「没连上」）

上一轮改成 `disconnect` + 重连，日志显示第二次启动**确实**打了 `hooked to the new launch task`，
但之后再没有一行 —— 因为连的是死对象。

**真正的原因在信号时序上**：

```cpp
// LaunchTask.cpp
std::unique_ptr<LaunchTask> LaunchTask::create(MinecraftInstance* inst) {
    auto task = std::unique_ptr<LaunchTask>(new LaunchTask(inst));
    task->init();          // ← 这里 setRunning(true) → runningStatusChanged(true)
    return task;           // ← 这时候 LaunchController 才把它写进 m_launchProcess
}
```

`runningStatusChanged(true)` 在 `m_launchProcess` 换成新任务**之前**就发出了。
于是 `hookTask()` 里 `getLaunchTask()` 拿到的是：

| | 第一次启动 | 第二次启动 |
| --- | --- | --- |
| `getLaunchTask()` | `nullptr`（还没建） | **上一次那个已结束的 LaunchTask** |
| 结果 | 重试 10 次后拿到新任务 ✅ | 立刻「连上」→ 连的是死对象 ❌ |

第一次能成、第二次起静默失效，就是这么来的。

**修法**：不再依赖信号，加一个 300ms 的核对定时器，每拍比较
`getLaunchTask()` 与成员 `QPointer<LaunchTask> m_hookedTask`，不一致就断开重连；
任务销毁时 `QPointer` 自动变空，也会重连。`runningStatusChanged(false)` 时清空并停表。

**实测**（同一会话连开两次，第二次用单实例转发 `atlas.exe --launch` 触发）：

```
 78.220  Map quit watcher: hooked to launch task 0x14f96c83cb0 pid -1     ← 旧任务（时序所致）
 78.985  Map quit watcher: hooked to launch task 0x14f9e4098d0 pid 13032  ← 765ms 后自动纠正到新任务
```

上一轮的代码就停在第一行，所以第二次永远收不到日志。

### 64. 视角锁死/狂转：先怀疑 quickPlay 无焦点（**误判**，真因是远控软件）

**当时的假设**：这是 Minecraft 自己的 bug（Mojira **MCL-24083**
《Quick play bug preventing mouse from being freely moved》，另有 MC-271193 / MC-274999 重复上报）。

> 用 quick play 启动、且游戏窗口出现时没有拿到焦点 → 游戏不显示暂停菜单、光标也没被真正捕获，
> 只能在窗口范围内乱动。上报者的临时解法是「按一下 Windows 键」。

按这个假设，我们这条路径的条件是"成立"的：你在 Atlas 窗口点「启动」，**Atlas 窗口还占着前台**，
游戏窗口是被创建出来的、拿不到前台 → MC 在 `screen == null` 那一帧 `grabMouse()` 失败 →
每帧读到的是窗口内的绝对坐标而不是相对增量 → 视角被顶到 ±90。

**修法**：新增 `launcher/maps/MapWindowFocus.{h,cpp}`。启动后每 250ms 找一次该进程的
GLFW 窗口，找到就把前台交过去（`AttachThreadInput` + `SetForegroundWindow`）。
两条约束：

- **只在「前台还是我们自己」或「压根没有前台」时动手** —— 你已经切到别的程序就绝不抢；
- 收工条件：**盯满 30 秒** 且游戏窗口连续 3 秒是前台。不能用「3 秒就收工」——
  启动器的进度框要等游戏进程起来才关（约 T+17s），它一关就可能把前台还回主窗口，
  而 quickPlay 真正 `grabMouse()` 在进图那一刻（约 T+25s），正好被这一下打中；
- 60 秒还拿不到就放弃，并打一行警告。

**当时的验证**：`Map window focus: launch task pid is now 16672` → `game window kept the foreground`
（从无窗口的后台进程拉起时，游戏窗口本来就拿到了前台，所以走的是「已在前台」分支）。

**最终结论（2026-11-03 19:00，用户实测）**：真因是**远程控制软件**（ToDesk / 向日葵）——
断开远控后视角完全正常，与启动器无关。上面这套推理虽然引用了真实存在的上游工单
（MCL-24083 确实存在），但**它不是本次症状的原因**：判断失误在于把「同一个症状」直接
归给了最像的已知缺陷，而没有先做「换个启动器 / 断开环境工具」的对照实验。

`MapWindowFocus` 保留：它对应的是 MCL-24083 那个真实缺陷，且只在「前台还是我们自己」时动手，
不改变正常行为；但要说清它**没有**修好这次的问题（见 [05](05-进度与遗留.md) §4.1）。

## 19. 导入 1.8.1 大图时「未响应」（2026-11-03）

用户导入 `E:/[1.8.1]大地复苏Terra Restore.zip`（162 MB、约 700 个 region），手动把版本改成 1.8.1 后，
窗口卡在「请稍候…（未响应）」，最后被结束。

**先定性**：Windows 事件日志是 `Application Hang (1002)`，不是崩溃；`instances/.tmp/4a97da`
留下 322 MB 解压到一半的存档，日志停在 `Extracted file r.9.1.mca`。

**根因**：`ProgressDialog::execWithTask` 用 `Qt::QueuedConnection` 调 `Task::start()`，
而 `Task::start()` 直接在 **GUI 线程**里跑 `executeTask()`；`MMCZip::extractSubDir` 是一次阻塞调用，
循环里不处理任何事件。12 MB 的图几秒就完了看不出来，162 MB 的图要几分钟 → 消息队列停摆 →
Windows 判定「未响应」。

**改法**：给 `MMCZip::extractSubDir` 加一个**默认空的进度回调**（`ExtractProgress`，
每解一个文件回调一次，返回 false 可中止）。调用方：

- `MapImportTask::extractWorlds`：`setStatus("正在解压存档… n / total")` + `setProgress(n, total)`
  + `QCoreApplication::processEvents(QEventLoop::ExcludeUserInputEvents)`；
- `reinstallWorlds`（实例页重装）：同样的 `processEvents`；
- 排除用户输入是故意的 —— 让对话框在解压期间无法被关掉，避免任务执行到一半对象被销毁。

顺带修了 `SingleZipPackInstallTask`：它把 `MMCZip::extractSubDir` 当函数指针交给 `QtConcurrent::run`，
多一个默认参数就推导不出 3 参数调用，改成 lambda。

**验证**：构建通过、`13 passed / 0 failed / 2 skipped`；`instances/.tmp` 已清理。
UI 是否真的不再假死需要用户复测（这次会话里无法自动点击导入）。

## 24. 预设的五处行为修正（2026-11-04）

### 24.1 取消勾选后按钮计数不变

## 25. 启动卡在「依赖库下载失败」：不是代码，是网络（2026-11-04）

### 25.1 现象

点「进入地图」后弹出「网络操作失败：实例 Torre de Piedra 的依赖库」，8 项请求只有 2 项成功，
其余是 `Operation canceled` / `Connection closed`；之后的几次尝试干脆什么都没发生。

### 25.2 诊断链

| 检查 | 结果 |
| --- | --- |
| `libraries/` 里 Fabric 相关 jar | **0 个** |
| `assets/objects` 相对 `1.21.1` 的 index | 缺 **110** 个（108 个语言文件 + 2 个） |
| 启动日志停在哪个任务 | `AssetUpdateTask`（资源没齐就不会启动游戏） |
| 官方资源域 | `resources.download.minecraft.net` 在本机 **TLS 握手直接失败**（curl 35） |
| 官方 Fabric maven | 8 个库里 6 个 `SSL handshake timed out` / `Connection closed` |
| BMCLAPI 同一路径 | 302 正常，跳转到 OpenBMCLAPI 节点 |

### 25.3 关键误判与纠正

一开始看到 BMCLAPI 的 302 目标（`bmclapi23.sakura.sld.tw` 等）握手失败，判断成"镜像坏了/路径错"。
按文档核对后路径完全正确：

| 官方 | 镜像 |
| --- | --- |
| `resources.download.minecraft.net` | `bmclapi2.bangbang93.com/assets` |
| `libraries.minecraft.net` | `bmclapi2.bangbang93.com/maven` |
| `maven.fabricmc.net` | `bmclapi2.bangbang93.com/maven` |

真正的原因是**本机环境有代理**（`http_proxy=127.0.0.1:6654`）：302 之后的节点被代理拒绝，
所以"镜像看起来不可用"。加 `--noproxy '*'` 直连后同一个 URL 立刻 `200`、585 KB 下载完成。
Python 批量脚本失败也是同一个原因（urllib 会自动读 `http_proxy`）。

> 结论：路径对、镜像在、节点可达。**问题出在"中间那层代理 + 官方域被断"**。

### 25.4 这一轮做了什么

- 从 `meta.prismlauncher.org` 取 `fabric-loader 0.20.1` 与 `intermediary 1.21.1` 的库列表，
  按 Maven 坐标补齐 8 个 jar；
- 解析 `assets/indexes/17.json`，用 BMCLAPI 补齐 108 个资源；`pls.json` / `qcb_es.json`
  两个节点反复断连，写了空 JSON 占位（海盗语与一种西语方言，不影响中文/英文，游戏只加载所选语言）；
- 验证：`javaw` 在 36 秒启动，日志走到 `Loaded 1274 recipes / 1399 advancements`，
  Fabric 数据包正常加载（`Found new data pack fabric`）。

### 25.5 结论（Prism 的下载机制适不适合国内）

它**不是坏的**，是**没为受限网络设计**：

1. 库与资源的 URL 写死在各家官方域，没有镜像概念；
2. 一个任务里任一文件失败，整个任务失败，不保留已成功的；
3. 重试只重试同一个域，等于再撞一次同一堵墙。

因此下一步加一个「下载源：官方 / BMCLAPI」开关（见 §26），**默认仍是官方**，不影响现有行为。

## 26. 下载源：可选 BMCLAPI 镜像（2026-11-04）

### 26.1 为什么

上一节（§25）确认了启动失败的真因：官方资源域在部分线路被 TLS 层直接重置，而启动器
**单源直连** —— URL 来自元数据的绝对地址，没有换源概念，一个文件失败整个任务失败。
玩家能做的只有反复重试或者手工补文件。

这一节加一个开关：**文件下载**可以整体走 BMCLAPI 镜像，且镜像请求不走代理。

### 26.2 改在哪一层

不在每个调用点改，而是在 `Net::Request::executeTask()` 里改一次 —— 资源、库、
版本 json、运行时清单，最终都从这儿出去，一处覆盖全部：

```cpp
m_url = Net::DownloadSource::rewrite(m_url);
if (Net::DownloadSource::isMirror(m_url))
    m_network = Net::DownloadSource::directNetwork();   // 直连，不继承启动器代理
```

**为什么不在构造函数里改**：重定向也会回到 `executeTask`。镜像返回 302 之后地址已经
变成节点域名，不在映射表里，`rewrite()` 对它是空操作 —— 若在构造时改，这段逻辑得写两遍
且容易对重定向的 URL 二次改写。

### 26.3 映射表（逐条照抄 BMCLAPI 文档）

| 官方 | 镜像 |
| --- | --- |
| `resources.download.minecraft.net/<xx>/<hash>` | `/assets/<xx>/<hash>` |
| `libraries.minecraft.net/<path>` | `/maven/<path>` |
| `maven.fabricmc.net/<path>` | `/maven/<path>` |
| `files.minecraftforge.net/maven/<path>` | `/maven/<path>` |
| `maven.neoforged.net/releases/<path>` | `/maven/<path>` |
| `maven.quiltmc.org/repository/release/<path>` | `/maven/<path>` |
| `meta.fabricmc.net/<path>` | `/fabric-meta/<path>` |
| `launchermeta` / `launcher.mojang.com` / `piston-meta` / `piston-data` | 路径原样拼到镜像根 |

**不映射**：Modrinth、CurseForge、GitHub、地图站、`meta.prismlauncher.org`。
另外同一域下不归镜像管的路径也保持原样（`files.minecraftforge.net/net/.../promotions_slim.json`）。

### 26.4 三个决定

1. **默认官方**。`DownloadSource` 默认 `official`；值不是 `bmclapi` 时 `rewrite()` 直接
   返回原 URL，官方路径的行为一个字节没变（这是用户明确要求的）。
2. **镜像走直连**。`directNetwork()` 是一条 `QNetworkProxy::NoProxy` 的
   `QNetworkAccessManager`。理由在 §25 里已经实测过：启动器/系统代理会把 BMCLAPI 的
   302 节点掐掉，换源反而更慢。
3. **映射错了必须能被测出来**。映射偏一位（比如 `/maven/` 少个斜杠）在界面上只表现为
   "下载失败"，会被当成网络问题排查半天。所以拆出纯函数 `mapToMirror()`（不看设置），
   用 `tests/DownloadSource_test.cpp` 把每一条映射、以及"不该改的没被改"都钉住。

## 28. 连通性测试"两个源都全红"：诊断与修正（2026-11-04）

用户点了「测试连通性…」，官方源和 BMCLAPI 都不通过。先给结论：**网络本身是通的，问题在
镜像的 CDN 节点，加上这个测试的设计太脆**。

### 28.1 先排除网络与 URL

同一台机器、同一时刻，四条测试地址直连（`--noproxy`）逐个测：

| 地址 | 官方 | 镜像 |
| --- | --- | --- |
| 版本清单 | 200 / 278 KB | 302 → 节点 |
| 游戏资源 | 200 / 586 KB | 200 / 586 KB |
| Mojang 库 | 200 / 80 KB | 200 / 80 KB |
| Fabric 库 | 200 / 1.9 MB | 200 / 1.9 MB |

所以 **URL 都是有效的，链路也通**。问题不在"网络设置错了"。

### 28.2 真正的原因：镜像的 302 有相当比例落到不可达节点

BMCLAPI 不直接返回文件，而是 302 到各 OpenBMCLAPI 节点。实测同一个 URL 连打五次：

```
try1 302 0b      ← 节点不可达
try2 200 90 KB
try3 302 0b
try4 200 278 KB
try5 302 0b
```

**单次成功率三到五成，且每次落到哪个节点是随机的。** 这是镜像的固有特性，不是配置问题。

### 28.3 这个测试原先为什么显得"全挂"

三个设计问题叠在一起，把"部分失败"放大成"整个功能坏了"：

1. **整包下载**：第四条拿的是 2 MB 的 `fabric-loader.jar`。弱网下这一条要几十秒，
   界面上就是一行"测试中…"不动 —— 看起来像卡死。
2. **失败即停**：任意一条失败就 `return`，后面的行永远停在"等待中…"。
   于是"第一条失败 + 三条等待"被读成"全都没连通"。
3. **不重试**：单次 30–50% 的成功率，压到一条 4 连测上，整体通过率只剩 8%–24%。

### 28.4 改法

| 改动 | 理由 |
| --- | --- |
| 第四条换成 `meta.fabricmc.net/v2/versions/loader` | 小 JSON，且镜像有对应的 `/fabric-meta`；测试是判通断，不是测带宽 |
| 每条最多试 **5 次**，间隔 400 ms | 每次重试都会重新 302 到另一个节点，五次后单条通过率约 95% |
| 一条失败**不再中断**，跑完再汇总 | 失败不连累后面的，最后给出 `n/4 通过` |
| 失败文案带 HTTP 状态码 | `302 Connection closed` 与纯 `Connection closed` 是两种问题，必须分得出来 |
| 失败行显示"换一个节点重试…"（橙色） | 让"重试中"和"失败"看起来不一样 |

用同一个临时环境变量钩子（验证完已删除）跑了两次真机：

- 第一次（3 次上限）：**3/4 通过** —— 两条是靠重试救回来的；
- 第二次（5 次上限）：**4/4 通过** —— 版本清单第 3 次成功、资源第 2 次、库第 3 次。

### 28.5 没做的那件事（要记着）

**真实下载仍然没有重试。** 镜像节点抖动时，`LibrariesTask` / `AssetUpdateTask` 会整体失败，
用户得手动点重试。之所以没顺手加，是因为重试要复用同一个 `Request` 对象，而 `FileSink`
可能已经写了一半数据 —— 重新 `init()` 是 truncate 还是 append 决定了会不会写出坏文件，
必须单独验证。**在验证之前不动网络层的重试逻辑。**

> 现实影响有限：失败是显式的（弹窗 + 重试按钮），且已下好的文件会在重试时被跳过。
> 但"镜像在弱网下更稳"这个卖点，目前只兑现了一半。

## 29. 真实下载的镜像换节点重试（2026-11-04）

接着 §28.5 那条"记着但没做"的事。

### 29.1 先回答卡住的那个问题：`FileSink` 重入会写坏文件吗

不会。三段代码合起来就能确认，不用靠"跑一次看看"：

1. `FileSink` 写的是 **`PSaveFile`（`QSaveFile`）**，数据先落到 `<目标>.XXXXXX` 临时文件，
   **只有 `commit()` 才改名成目标文件**；
2. `open(QIODevice::WriteOnly)` 打开的是一个新的临时文件（不是目标文件的追加句柄），
   所以重入 `init()` 是"从零写"；
3. 失败路径走 `abort()` → `cancelWriting()`，临时文件被删掉，目标位置上**上一次的好文件
   还在**，玩家不会因为一次网络抖动丢掉一个能用的 jar。

`init()` 里原来靠的是"`unique_ptr::reset` 先析构旧的 `QSaveFile`（析构即 `cancelWriting`）"，
虽然也对，但读代码看不出保证。现在改成显式 `cancelWriting()` + `reset()`，把语义写死，
并由 `tests/RequestRetry_test.cpp` 三个用例（重入 `init`、`abort` 后重来、校验器重置）钉住。

### 29.2 重试怎么做

| 决定 | 理由 |
| --- | --- |
| **回到镜像入口重试，不是重试失败的节点** | 302 之后 `m_url` 已经是节点域名；接着打同一个节点等于确定性失败。回到 `m_mirrorBaseUrl` 才会重新 302 到另一个节点 |
| 最多 **3 次**（总尝试 4 次） | 单次成功率 40% 时，4 次后失败概率约 13%；每次重试都要从头下整个文件，再多就是拿带宽赌运气 |
| 只认**连接层面**的错误 | `RemoteHostClosed` / `ConnectionRefused` / `HostNotFound` / `Timeout` / `TemporaryNetworkFailure` / `NetworkSessionFailed`。一旦对面给过 4xx/5xx 就放弃 —— 换节点不会把 404 变成 200 |
| 只重试 **GET** | 重发 POST 可能造成重复副作用；镜像请求本来就全是 GET |
| 重试前 `m_sink->abort()` | 丢掉半截数据、作废哈希；下一轮 `init()` 重建临时文件 |
| 用 `QTimer`（400 ms × 第几次）而不是立刻重发 | 现在还在 `QNetworkReply::finished` 的槽里，立刻 `m_reply.reset()` 等于在信号派发过程中析构发信号的对象 |
| 官方源**一个字节都不动** | 没有 `m_mirrorBaseUrl` 就永远不重试；这条和 §26.4 的"默认官方"是同一个约束 |
| 新增 `Option::NoMirrorRetry` | 连通性测试自己就是那层"每条 5 次"的重试，再叠一层会变成 20 个请求、界面上的"第 n 次"也对不上 |

日志（`launcher.task.net.download`，Warning 级）：

```
Mirror node failed: "https://node-7…/file.jar" ( "Connection closed" ) - retrying from "https://bmclapi2.bangbang93.com/maven/x.jar" (1/3)
```

状态栏同时显示「镜像节点无响应，正在换节点重试（n/3）」，进度归零重新计。

> 和 `NetJob` 自带的任务级重试（`NetworkRetryLimit`，默认 3）是两层，不冲突：
> 这一层负责"一个节点抖一下别把整个任务打挂"，任务级那层负责"整轮重来"。
> 代价是同一个永远连不上的地址最坏会被打 4×3 次，所以只对**镜像**开（官方源不重试）。

### 29.3 顺手修的一处：`Request` 不能假设自己跑在 `Application` 里

`executeTask()` 里三处 `APPLICATION->…`（网络管理器、UA、超时）用的是 `static_cast`，
单测里 `qApp` 是个普通 `QCoreApplication`，转换出来的指针是假的，一取 `settings()` 就崩。
改成 `APPLICATION_DYN`（`dynamic_cast`）+ 空值回退，真机行为不变，`Request` 也能在没有
`Application` 的上下文里跑 —— 这也是能把下面那条全链路用例写出来的前提。

## 30. "下载很慢、bmclapi 全红、装不上游戏"：一次现场取证（2026-11-04）

三条抱怨其实是三件独立的事。先摆证据，再说改了什么。

### 30.1 现场证据

`atlas.cfg`：`DownloadSource=official`、`RequestTimeout=60`、`NumberOfConcurrentDownloads=6`、
`ProxyType=None`、`NetworkRetryLimit=2`。

日志（`Atlas-0.log`）里失败的请求，**每一条都精确在开始后 60.0 秒被中止**：

| 请求 | 开始 | 中止 | 差 |
| --- | --- | --- | --- |
| `netty-common-4.2.7.Final.jar` | 263.430 | 323.431 | **60.0 s** |
| `netty-handler-4.2.7.Final.jar` | 266.981 | 327.000 | **60.0 s** |
| `netty-resolver-4.2.7.Final.jar` | 268.888 | 328.894 | **60.0 s** |
| `netty-transport-classes-epoll-…jar` | 281.937 | 341.965 | **60.0 s** |

而在同一条连接上，`netty-codec-http` 从 263.189 一路下到 338.200（**75 秒，成功**）。
也就是：**同一个 h2 连接、同一个时刻，一条流在慢慢收数据，另一条整整 60 秒零字节。**

同一台机器、同一时段的实测（`curl --noproxy '*'`，各 3 次）：

| 目标 | 结果 |
| --- | --- |
| `libraries.minecraft.net`（Azure Edge） | 0.9–1.2 MB/s；**低峰时段只有 30–61 KB/s** |
| `piston-data.mojang.com/client.jar`（31 MB） | 3.2–3.7 MB/s，h2 与 h1.1 持平 |
| 6 并发到 `libraries`（复刻启动器配置） | 合计 **1.86 MB/s**，h2 与 h1.1 完全一致 |
| `bmclapi2.bangbang93.com/maven/…` | 302 → 有时 `cmcc.mirrors.ustc.edu.cn`（**1.3 MB/s**），更多时候是 `*.sakura.sld.tw` / `*.sakura.exp.dog` → **`curl: (35) Recv failure: Connection was reset`** |

### 30.2 三个结论

1. **"慢"不是启动器造成的。** 这条线路对官方 CDN 的吞吐本身就在 30 KB/s – 1.2 MB/s 之间摆，
   6 并发能跑满 1.86 MB/s。界面上 63 KiB/s 是落在低谷期（另外 DNS 间歇失败也在吃时间）。
2. **"bmclapi 全不达"是节点抽签，不是配置错。** 入口秒回 302，坏的是 302 指出去的节点：
   这条线路对 `*.sakura.sld.tw` / `*.sakura.exp.dog` 做 TLS 重置，日志里表现为
   `HTTP status: 302 "Connection closed"`。官方 Azure 没被断，只是慢 —— 所以"官方绿、镜像红"。
3. **"装不上游戏"是我方的 bug。** `RequestTimeout` 到期时 Qt 会 `abort()` 正在跑的 reply，
   报 `OperationCanceledError`；而代码把它当成"用户点了中止"（`Aborted`），**不重试、只报
   `Operation canceled`**。4 个文件被这样掐掉 → `LibrariesTask` 整体失败 → 实例起不来。

### 30.3 改了什么

| 改动 | 理由 |
| --- | --- |
| `OperationCanceledError` 归类为**网络停滞**，可重试、并给出人话（"网络停滞：长时间收不到数据（已重试 n 次）"） | 用户主动取消走 `Request::abort()`，那条路已断开 `errorOccurred`，进不到这里 —— 能收到的取消只有传输超时 |
| 重试对**官方源也生效**（原先只有镜像） | Azure CDN 同样会 `Connection closed`，而且它就是本条线路的常态 |
| 重试预算（3 次）用尽后，镜像**回落官方源一次** | 用户选镜像的初衷是"快"，不是"宁可不下载"。回落是单向的，不会官方失败又切回镜像绕圈（`shouldFallBackToOfficial` 钉住） |
| **文件下载禁用 HTTP/2**（`FileSink` 类型的 sink） | 上面那条"一条流 75 秒、另一条 60 秒零字节"就是 h2 单连接的多流互相饿死；h1.1 下每个文件一条连接，互不牵连。JSON/API 请求继续用 h2（多路复用对它们是赚的） |

## 31. 下载提速：QNAM 连接池（2026-11-04）

"下载还是慢"之后去看参考实现，发现两边都是靠**多连接**换带宽，而我们只有一条连接一个文件。

### 31.1 参考实现怎么做的

| | HMCL | PCL2 |
| --- | --- | --- |
| 做法 | 单文件单连接，**同时下 N 个文件**（`DEFAULT_CONCURRENCY = min(核数×4, 64)`） | **单文件切成多段**，每段一条连接（`ToolDownloadThread` 默认 63，+1 = 64 条线程） |
| 代价 | 只是并发度 | Range 头、`.part` 文件、乱序写、合并、校验 |

### 31.2 这条线路的实测：带宽按"连接"分配

同一个 24 MB 文件、同时刻、分段并发（`curl -r`）：

| 连接数 | 10 秒下到 | 折算 |
| --- | --- | --- |
| 1 | 622 KB | **60 KB/s** |
| 4 | 835 KB | 81 KB/s |
| 8 | 4.99 MB | **487 KB/s** |
| 32 | 12.18 MB | **1189 KB/s** |

不是"网慢"，是**每条连接被限速**。所以别人快，是因为他们把连接数堆上去了。

### 31.3 关键发现：一个 QNAM 每主机只有 6 条连接

Qt 的 `QNetworkAccessManager` 对同一主机固定最多开 6 条 HTTP/1.1 连接
（`QHttpNetworkConnection` 的默认值，公开 API 改不了）。

Atlas 原来的 `NumberOfConcurrentDownloads = 6` **正好把这个额度占满**——
所以"把并发数改到 64"是没用的，Qt 只会把多出来的请求排队复用那 6 条连接。
这也解释了为什么 h2 关掉之后（§30）速度并没有质变：仍然是 6 条。

解法：**多个 QNAM 组成连接池**。每个 QNAM 各自维护 6 条/主机，4 个就是 24 条。

### 31.4 改了什么

| 改动 | 说明 |
| --- | --- |
| `Application::downloadNetwork()` | 4 个 QNAM 的池，惰性创建、轮转分配；改代理时同步更新池内每个 QNAM（否则改完代理要重启） |
| `Request::executeTask()` | **只对文件下载**（sink 是 `FileSink`/`MetaCacheSink`）用池；JSON/API 请求仍在主 QNAM，避免打散会话 |
| `NumberOfConcurrentDownloads` 默认 6 → **24** | 池有 4×6 条连接，24 个并发文件才真的能开满；便携配置里的旧值也同步成了 24 |
| `DownloadChunks` 默认 **0（关闭）** | 单文件分段（PCL2 式）当时还在验证中；**从 §32 起改为 8** |

### 31.5 验证

| 项 | 结果 |
| --- | --- |
| 编译 | ✅ `atlas.exe` / `LauncherTests.exe`（`Application.h` 改动会触发全量重编，约 8 分钟；并行度 >3 时容易撞 `C1083`，`CMAKE_BUILD_PARALLEL_LEVEL=3` 稳定） |
| 单测 | ✅ 四套 **52 passed / 0 failed / 2 skipped** |
| 连接池对比（真实网络） | ✅ 同一批 12 个库文件（7381 KB）：**1 个 QNAM 35.2 s / 209 KB/s**，**4 个 QNAM 15.8 s / 467 KB/s（2.2×）**，两次都 12/12 成功 |
| 真机观感 | ✅ 已复看（2026-11-05）：批量下载明显变快；大文件另见 §33 |

> 2.2× 而不是 4×：这条线路上限本身就在 1–1.9 MB/s 之间浮动（§30 实测），
> 24 条连接已经接近封顶，再堆连接收益递减。

| # | 结论 |
| --- | --- |
| 96 | 📌 **一个 QNAM = 每主机 6 条连接**；想真并发必须有 QNAM 池，改设置里的并发数没有用 |

## 32. 大文件分片下载：做成可配置项（2026-11-04）

§31 的连接池只解决"很多文件同时下"；**只剩最后一个大文件时，仍然只有一条连接**（30–60 KB/s）。
这一节把 PCL2 式的"单文件切多段"补完，并做成设置项。

### 32.1 做法

| 环节 | 实现 |
| --- | --- |
| 何时拆 | 首个响应是干净的 200、带 `Content-Length`、且 ≥ 1 MB，才拆（`PARALLEL_MIN_SIZE`） |
| 怎么拆 | `Request::splitChunks(total, count)` 切成无缝无重叠的 `[start, end]`，段数不超过字节数（否则会出现长度为 0 的分片，Range 直接 416） |
| 怎么丢原连接 | 一旦决定拆，**丢掉那条没带 Range 的响应**——它会把整个文件拉回来并覆盖别的分片。N 条带 `Range` 的请求全部重开 |
| 写到哪 | 目标文件旁边写 `<目标>.part`（普通 QFile，可 seek），完成后关文件 → **整份按顺序喂一遍校验器** → 删旧文件 → rename。中途失败只删 `.part`，目标位置原有的好文件不受影响 |
| 每片连接 | 每个分片**轮转取一个池内 QNAM**：一个 QNAM 每主机只有 6 条连接（§31），8 片挤在一个 QNAM 上等于还是 6 条 |
| 单片失败 | 只重试这一片（最多 3 次，200 ms 间隔），不把整个文件拖回单连接 |
| 服务器不认 Range | 分片返回 200（而不是 206）→ 立刻整体降级为单连接，不再傻重试 |
| 彻底失败 | 降级一次后仍失败，才走原有的重试/失败路径 |

### 32.2 设置项

`设置 → 启动器 → 任务` 新增「**大文件分片下载**」（`DownloadChunks`，0–32，默认 **8**）：
- `0`/`1` = 关闭；`8` 段在弱网下实测能快一个数量级；
- 只影响 ≥ 1 MB 的文件，小文件（库、json）不受影响；
- 连接池 4 × 6 = 24 条，8 片只用到其中一部分，给并发文件留了余量。

### 32.3 验证

| 项 | 结果 |
| --- | --- |
| 单测 | ✅ `RequestRetry_test` 16 项（新增切分连续性、乱序写入、校验失败不落盘）；四套合计 **55 passed / 0 failed / 2 skipped** |
| 真实网络（同一 24 MB 文件，`fastutil-8.5.18.jar`） | 单连接 **237144 ms / 98 KB/s**；8 段 **7039 ms / 3324 KB/s**；两次 sha1 均与官方一致（`a6cff377…`） |
| Range 不支持时的降级 | 代码路径 + 单测覆盖，真机未遇到（Mojang / BMCLAPI 都支持 Range） |
| 真机验收 | ⏳ 修复后尚未复看（§33）；探针已用同一个 `client.jar` 验证过 |

| # | 结论 |
| --- | --- |
| 100 | ✅ 大文件分段并发落地，实测 24 MB 文件 98 KB/s → 3324 KB/s，sha1 一致 |
| 101 | 📌 拆段前必须丢掉那条无 Range 的响应，否则它会覆盖其他分片 |
| 102 | 📌 分段写入不过校验器，必须在 finalize 时把 `.part` 按顺序喂一遍，校验不过不许落盘 |

## 33. 分片下载真的跑起来了：三个 bug（2026-11-05）

§32 上线后用户实测：`client.jar`（28 MB）仍然只有 368 KB/s，日志显示**切了 8 段，但 5 秒后
两片报错、10 秒后整体降级回单连接**。三个都是"只有真跑才会暴露"的问题。

### 33.1 一次失败被记成两次

```
51.747 Range 6 failed: RemoteHostClosedError
51.747 Retrying range 6 attempt 1     ← errorOccurred
51.747 Retrying range 6 attempt 2     ← 紧接着的 finished，又记一次
```

`onChunkError` 和 `onChunkFinished` 都调了 `retryChunk`，而 `errorOccurred` 之后必然跟一个
`finished`。于是 3 次上限实际只有 1.5 次。**改成只由 `finished` 决定重试**，`errorOccurred` 只记日志。

### 33.2 一片失败就从头再拉

原来 `retryChunk` 把 `received` 清零。弱网下一片动辄几 MB，一条连接断了就全白下。
现在 `startChunk()` 从 `chunk.start + chunk.received` 续（`Range: bytes=<已收>-<片尾>`），
**分片级断点续传**；重试上限提到 6 次，退避 300 ms × 次数。

### 33.3 在 `metaDataChanged` 里析构 reply → 整个 QNAM 挂死

决定拆段时要丢掉那条没带 `Range` 的响应。原来的写法是 `m_reply.reset()`，而我们正处在
**这个 reply 自己的 `metaDataChanged` 信号**里。结果：8 个分片请求发出去后**一个信号都不回**，
5 分钟超时（探针复现）。改成 `release()` → `disconnect` → `abort()` → `deleteLater()`，
把析构交给事件循环。

### 33.4 验证

| 项 | 结果 |
| --- | --- |
| 单测 | ✅ 四套 **55 passed / 0 failed / 2 skipped** |
| 真实网络（用户失败的那个 `client.jar`，29525242 B / sha1 `a19d9bad…`） | ✅ **9617 ms / 2998 KB/s / sha1 一致**；用户实测那次是 368 KB/s、约 80 秒 |
| 复现旧 bug | ✅ 未修 `deleteLater` 时探针 300 s 超时、日志里只有 "Splitting" 一行 |

| # | 结论 |
| --- | --- |
| 104 | 📌 分片的重试只能有一个入口（`finished`），`errorOccurred` 紧跟其后，两处都重试等于砍半 |
| 105 | ✅ 分片失败从断点续（`Range: bytes=已收-`），不再整片重下 |
| 106 | 📌 **绝不能在 reply 自己的信号里析构它**：`metaDataChanged` 里 `reset()` 会让 QNAM 之后所有请求静默挂死；必须 `deleteLater()` |

## 34. 资源库的边界：assets 不是全部，还有一本账（2026-11-05）

用户问"换资源库是不是只换 `assets/`？删掉就能重下吗？"。查代码时发现两件事：一件是概念
（哪些目录算共享资源、靠什么判定"已下载"），一件是真 bug。

### 34.1 概念：四块目录 + 一本账

| 位置 | 判定依据 | 只拷它会怎样 |
| --- | --- | --- |
| `assets/objects` | 文件在 + **大小一致**（`AssetObject::getDownloadAction`） | ✅ 直接可用，不需要账本 |
| `assets/indexes` | metacache + ETag，且每次启动都条件请求 | 会重下（几百 KB，无所谓） |
| `libraries/`（含 client jar） | **metacache**（`Library::getDownloads` → `resolveEntry`） | 文件都在也会**整份重下** |
| `java/` | 目录存在 | 重下约 500 MB |
| `meta/` | metacache | 重下（几 MB） |
| `metacache`（文件） | — | 是上面两行的账本；删了＝库全部重下 |

`resolveEntry()` 的兜底很关键：条目在、文件在、但 mtime 变了，会**重算 md5** 比对；
一致就更新时间戳继续认账。所以复制（mtime 必变）不会导致误判重下。

### 34.2 修掉的 bug：`assets/objects` 不认共享目录

`AssetObject::getLocalPath()` 返回的是硬编码相对路径 `"assets/objects/<xx>/<hash>"`，而
`assets/indexes`、`assets_root`、`librariesPath()` 都已改走 `resource::assetsDir()`。
设了「共享资源目录」之后：素材被下到**数据目录**、游戏却去**共享目录**读 —— 看起来像
"素材反复重下且没有声音/贴图"。改为 `FS::PathCombine(resource::assetsDir(), "objects", rel)`，
与其它路径同源；没设共享目录时结果与旧行为逐字节相同（都落在数据目录）。

### 34.3 顺带补的：老数据目录自动迁移漏了三样

`Application::performMigration()`（从旧版本数据目录搬过来）的过滤器原本只有
`assets/ libraries/ instances/ mods/ icons/ themes/ logs/`，**漏了 `meta/`、`java/`、`metacache`**：
搬完的结果是"资源库只搬了一半"，库文件因为账本没过来而全部重下。已补三个过滤器。

### 34.4 验证

| 项 | 结果 |
| --- | --- |
| 编译 | ✅ `atlas.exe` / `LauncherTests.exe` |
| 单测 | ✅ 四套 **55 passed / 0 failed / 2 skipped** |
| 默认路径行为 | ✅ 本机 `SharedResourceDir` 为空，`assetsDir()` = 数据目录，路径与改动前一致 |
| 共享目录生效 | ⏳ 未真机验证（需要改设置 + 重启 + 进游戏看有没有声音/贴图）；路径已与 `assets_root` 同源，单测覆盖不到（`resource::assetsDir()` 依赖 `APPLICATION`） |

| # | 结论 |
| --- | --- |
| 107 | 📌 资源库 = `assets` + `libraries` + `java` + `meta` + **`metacache`**；只搬 `assets` 不够 |
| 108 | 📌 库文件靠 `metacache` 认账（条目缺失＝重下），素材只靠"存在 + 大小"，两者的迁移要求不一样 |
| 109 | ✅ 修掉 `AssetObject::getLocalPath()` 硬编码相对路径，以及数据目录自动迁移漏搬 `meta/java/metacache` |

## 35. 拿"下载全部正式版资源"压测下载栈（2026-11-05）

设置 → 启动器 → 任务里加了一个**临时**按钮（`#ifndef NDEBUG`，随调试期删）：遍历版本清单里
全部 103 个正式版，用启动器自己的路径把 client jar / 库 / 素材索引 / 素材对象下到当前数据目录。
另有两个环境变量供无人值守：`PRISM_DEBUG_DOWNLOAD_ALL=1` 打开即跑，`PRISM_DEBUG_DOWNLOAD_LIMIT=N`
只跑前 N 个。跑完在 `logs/resources-all-versions.txt` 落一份逐版本报告。

它做的事和玩家真实下载完全同源（`Library::getDownloads()`、`AssetsIndex::getDownloadJob()`），
所以下面这些问题是"真跑才看得见"的。

### 35.1 连接池从上线起就没被用过（§31 是死代码）

`NetJob::addNetAction()` 对每个请求都 `setNetwork(m_network)`，而 `Request::executeTask()` 只在
`m_network == nullptr` 时才去挑 QNAM 池 —— 只要请求是在 NetJob 里跑的（**资产、库、client jar 全都是**），
连接池就永远不会被选中，实际仍然是一个 QNAM 的 6 条连接。

§31 的"209 → 467 KB/s"是合成测试（自建 QNAM）测出来的，真机从没验证过这一点。

改成：**文件下载（sink 是 `FileSink`）在 Application 存在时总是走池**，其余（JSON/API）留在主 QNAM。
单测路径（没有 Application）不受影响，仍用调用方给的 QNAM。

### 35.2 1 MB 的库也拆 8 段

`PARALLEL_MIN_SIZE` 原来是 1 MB，于是 60 个 1 MB 的小库各自拆 8 条连接：**握手开销 ×8、请求数 ×8、
对端连接数一度超过 190**。日志里全是 `Splitting 1255440 bytes into 8 ranges`。

阈值改成 **4 MB**：client jar（30–41 MB）、fastutil（24 MB）继续拆；lwjgl 这类 1.2 MB 的走单连接。
实测 A/B：删掉 1.2 MB 的 `lwjgl-3.4.3.jar` 和 41 MB 的 `26.3-client.jar` 后重跑 ——
前者单连接一次过，后者仍然 `Splitting 41483720 bytes into 8 ranges`。

### 35.3 零进展的分片会硬试 6 次（最坏 6 分钟）

`piston-data` 的 26.1.2 `client.jar`（38 MB）：某一段连续两次一个字节都没进来，每次都要等
`RequestTimeout=60` 秒超时，然后**从同一个偏移**再试 —— 6 次上限意味着 6 分钟白等。

新增 `MAX_ZERO_PROGRESS_ATTEMPTS = 2`：连续两次"没有进展"就放弃分片、退回单连接。
实测降级在 20 秒内完成（`Range 7 made no progress in 2 attempts, giving up on chunking`）。

> 代价：单连接在这条线路上只有 **94 KB/s**，41 MB 要 468 秒。所以这是"止损"，不是"优化"——
> 更好的做法是降级到 4 段而不是直接单连接（记在 05 §6）。

### 35.4 调试工具自己的 bug：没按规则过滤

第一版直接遍历 `versionFile->libraries` 调 `getDownloads()`，结果把 **linux / macOS 的 natives
也下了一遍**（`jtracy-...-natives-linux.jar`、`netty-...-osx-aarch_64.jar`）。补上
`library->isActive(context)`（真实流程里由 `profile->getLibraries()` 完成过滤）。

### 35.5 去重的实测效果

| 版本 | 需要下载 | 素材命中 |
| --- | --- | --- |
| 26.3（首个） | 62 项（client 1 / 库 60 / 索引 1） | 607 / 5147 |
| 26.2 | 60 项（client 1 / 库 58 / 索引 1） | **51 / 5057** |
| 26.1.2 | 4 项（client 1 / 库 2 / 索引 1） | 13 / 4750 |
| 26.1.1 | **1 项**（只有 client jar） | 0 / 4569 |

库和素材的复用几乎立竿见影：26.1.1 和 26.1.2 共用同一批库，所以只差一个 jar。

## 36. 卡 29 分钟的根因：重试从第 0 字节重来（2026-11-05）

用户截图停在 1.17.1 的 9/11。查日志，同一个 19.5 MB 的 `client.jar` **从 1089s 卡到 2829s
（29 分钟），6 次尝试全部失败**，而且每次都从 0 开始。

### 36.1 为什么"永远下不完"

失败原因清一色是 `RemoteHostClosedError`（`Connection closed`）—— 不是超时、不是 404，
是 CDN 传到一半把连接掐了。三个数字放一起就明白了：

| 量 | 实测 |
| --- | --- |
| 这条线路单连接吞吐 | ~90 KB/s |
| 19.5 MB 需要的时间 | ~3.5 分钟 |
| CDN 掐连接的间隔 | 1–8 分钟（随机，越接近完成越容易撞上） |

**下载耗时 > 连接寿命**，而每次重试又从 0 开始 → 每次都在完成前被掐 → 永远下不完。
`NetJob` 自己的 3 次重试也是"整份重来"，所以两层重试叠加仍然无限循环。

次要因素：分片失败一次就 `m_parallelDisabled = true` 永久退回单连接，而单连接恰恰是最容易被掐的形态。

### 36.2 改了什么（下载模块，与调试工具无关）

| 改动 | 说明 |
| --- | --- |
| 顺序下载改用 `<目标>.part`（普通 `QFile`） | 不再用 `QSaveFile` 的隐藏临时文件 —— 那个文件一旦 `abort()` 就没了，续传无从谈起 |
| `FileSink::init()` 发现 `.part` 有数据就带 `Range: bytes=N-` | 断点续传的入口；顺便把已有字节**补喂**给校验器（否则 sha1 永远对不上） |
| 服务器无视 Range（返回 200）时 `restartFromZero()` | 丢掉半截重写，否则会 append 出一个"内容 ×2"的文件 |
| `finalize()` 对 206 强校验长度 | `Content-Length + 断点` 就是完整长度；不完整时**不落盘、保留 `.part`** 等下一轮 |
| 失败/重试不再 `abort()` sink | 只有用户取消才删 `.part`；`NetJob` 级重试因此也能接上 |
| 进度条加上断点前缀 | 续传时进度不再从 0 跳 |

### 36.3 验证

| 项 | 结果 |
| --- | --- |
| 单测 | ✅ `RequestRetry_test` **19 项**（新增：续传、服务器无视 Range、校验器补喂、206 不完整保留 `.part`） |
| 真实网络（端到端） | ✅ 取一个 1 MB 素材对象，先塞 100 KB 到 `.part`：日志 `Resuming … from byte 102400` → 服务端 206 → 续完 → **sha1 与文件名一致**、`.part` 已清理 |
| 分片层 | ✅ 26.3 的 41 MB client.jar：第 6 片下到 **31112790 字节**后才断，日志 `Retrying range 6 … from offset 31112790`（不是从片头） |
| 仍要真机观察 | ⏳ `Connection closed` 频繁时的连续续传（本轮网络恰好没触发到"单连接 + 续传"的组合） |

### 36.4 代价与遗留

- 失败时会留下 `<目标>.part`（最多一个文件大小）。进程被强杀也可能留下 —— 目前没有启动期清理，
  记在 05 §6。
- 如果服务器上的文件更新了，旧 `.part` 的前缀就是错的：校验会失败 → 删掉重下一次。没有做
  "先比对 ETag/Last-Modified 再决定续不续"的优化。
- 分片失败仍会永久退回单连接（`m_parallelDisabled`），但现在单连接能续传，所以不再是死路。

### 36.5 顺手堵掉一个更危险的口子：分片的预分配文件

分片模式会先把 `.part` **resize 到总长度**（这样各分片能直接 seek 到自己那一段）。
一旦分片失败、退回顺序下载，`init()` 看到的是一个「满尺寸」的 `.part` —— 会以为整个文件都下完了，
发 `Range: bytes=<总长>-`（服务器直接 416），或者更糟：把中间的空洞当成数据。

改成分片用独立文件名 `<目标>.part.parallel`，顺序 `init()` 会把它直接删掉。
顺序下载的 `.part` 永远是「从 0 开始的连续前缀」，两种语义不再混用。
单测 `parallelScratchIsNotUsedAsResumePrefix` 钉住。

| --- | --- |
| 115 | 📌 弱网下的第一性问题是**能不能续传**，不是并发数：下载耗时 > 连接寿命时，不续传就等于永远失败 |
| 116 | ✅ 顺序下载改走 `<目标>.part` + `Range`，失败保留半截，`NetJob` 级重试也能接上 |
| 117 | 📌 续传必须把已有字节补喂校验器，且服务器无视 Range 时要 `restartFromZero()` |
| 118 | 📌 `.part` 残留没有自动清理（进程被强杀时最明显），列进 05 §6 |
| 119 | 📌 分片的预分配临时文件必须与顺序下载的断点文件分开命名，否则「满尺寸 + 空洞」会被当成完整文件 |

## 37. "又卡住了"：死连接没有闸门，官方源也没有退路（2026-11-05 下午）

截图停在 1.16.5（35/103，步骤 0/1）。日志里这条版本 json 请求从 1156.8s 起，
**59 秒里没有一行日志**，用户在 1215.5s 关掉了程序。

### 37.1 两个问题

1. **"零响应"只能等满 `RequestTimeout`（60 秒）**。请求已经发出去、服务器既不回包也不断开，
   Qt 的传输超时从"最后一次收到数据"算起，所以连响应头都没见到时也要干等 60 秒。
   一个 20 KB 的版本 json 卡一分钟，界面看起来就是死住。
2. **官方源没有退路**。我们早就有"镜像用满 3 次 → 回落官方"，但反方向没有：
   用户选了官方源、官方又在 stall 时，只能耗完 3 次预算然后失败。
   而 `piston-meta` 正是今天一直在 stall 的那个域（镜像映射表里其实有它）。

### 37.2 改了什么

| 改动 | 说明 |
| --- | --- |
| **20 秒零响应看门狗** | 建好 reply 就起表；收到响应头（`metaDataChanged`）或任何数据就停表。到点仍无响应 → 记为"停滞"、abort 当前尝试、走正常重试（有 `.part` 就续传） |
| **官方 → 镜像回落** | 与"镜像 → 官方"对称，各只走一次（两个方向互斥，不会绕圈）。回落后给镜像一整轮预算，状态栏提示"官方源长时间无响应，已改用镜像重试" |
| **416 Range 越界** | `.part` 不小于文件长度时（下完但没来得及收尾）服务器会回 416；原来每次重试都 416 → 死循环。现在丢掉半截重来 |
| 调试入口加 `PRISM_DEBUG_DOWNLOAD_ONLY=<版本>` | 排查单个版本时不用跑全量（本次就是用它定位 1.16.5） |

### 37.3 验证

| 项 | 结果 |
| --- | --- |
| 真机（1.16.5，官方源，piston-meta 正在 stall） | ✅ `3.4s` 发起 → **`23.4s` 看门狗触发**（不再等 60 秒）→ `24.0s` 重试 → **`25.8s` 成功**，版本 json 落盘 |
| 单测 | ✅ `RequestRetry_test` **21 项**（新增：官方连续失败回落镜像，5 次请求的第 5 次是镜像地址） |
| 既有用例修正 | `stallFailureIsReadable` 改用没有镜像映射的域（`textures.minecraft.net`），否则新增的回落会把它变成"还有一轮"，测不到文案 |
| 全套 | ✅ 60 passed / 0 failed / 2 skipped |

### 37.4 仍然存在

- 看门狗只覆盖"连响应头都没有"；**有响应头但 body 慢慢爬** 仍由 60 秒传输超时判定。
  这属于用户设置项，没有动。
- 官方→镜像回落对 `piston-meta` 有效，但如果镜像自己也抽到坏节点，仍然会失败——
  只是多了一条路，不是保险。
