## 1. 网络与阻断

### 1.1 `*.supabase.co` 被封的是 **SNI 字符串**，不是 IP

2026-11-01 把可能性一条条排掉：

| 试法 | 结果 |
| --- | --- |
| DNS 解析 | ✅ 正常（Cloudflare `104.18.38.10` / `172.64.149.246`，不是污染） |
| HTTPS 根路径 | ❌ `Connection was reset` |
| `--tls-max 1.2` / `--http1.1` | ❌ 一样 reset（不是 ALPN/TLS 版本问题） |
| 明文 `:80` | ❌ 同样 reset（不是"只掐 TLS"） |
| 换端口 8443 / 2053 / 2083 / 2087 / 2096 | ❌ 全 reset（不是"只封 443"） |
| 同一 IP、**把 SNI 换成 `api.modrinth.com`** | ✅ **200** |
| `https://www.ctmmaps.com/` | ✅ 200（站点在 Vercel，本身没被封） |

结论：**被封的是 `*.supabase.co` 这个 SNI 字符串**。浏览器能过是因为 Chromium 实现了
**ECH / GREASE**（握手内容里看不出目标域名）；Qt 在 Windows 走 Schannel，
只能把 SNI 写在明文里，发出去就被 RST。

所以产品里给了四条路（前三条已实现）：**浏览器通道**（默认）→ 代理（`HallProxy` auto）→
Cloudflare Workers 反代模板 → 离线（打开原站挑、下载完再导入）。

> 不要试图自己实现 HTTP/3：Qt 6.8 没有 QUIC，而浏览器就在本机，借它更省事。

### 1.2 `net::ERR_CONNECTION_RESET` 是概率性的

同一条 REST/图片 URL 实测约 **1/3 概率**被 reset。任何"一次请求定生死"的写法都会偶发失败：
重试必须放在**页面内**（XHR + 退避），而不是"失败就重开一个浏览器进程"。

### 1.3 浏览器通道的两个硬性参数

- **不能加防缓存参数**：PostgREST 对未知查询参数返回 `PGRST100 / unexpected param`（400），
  `?_r=1` 这种会让重试全灭；
- **`--disable-web-security` 必须有**：跨域图片画进 canvas 会 tainted，`toDataURL` 直接抛异常。
  用一次性空白 profile、只加载自己生成的临时页面，跑完即杀。

### 1.4 元数据镜像导致的"列表更新失败"

`Connection closed` 常常不是代码问题，而是设置里 `MetaURLOverride` 指向了一个失效镜像。
排查：`atlas.cfg` 里搜 `MetaURLOverride` → 清空 → 确认
`https://meta.prismlauncher.org/v1/index.json` 返回 200。

## 2. Windows / 工具链

1. **环境里同时有 `HTTP_PROXY` / `http_proxy` / `HTTPS_PROXY` / `https_proxy`** 四个键时，
   `Enter-VsDevShell` 会抛 `ArgumentException`（键冲突）。进 PowerShell 先清进程级变量。
2. **`bootstrap-vcpkg.bat` 失败**（`SetFileInformationByHandle error 0x5 拒绝访问`）：
   手动下载 `vcpkg.exe`（对应 release）放进 vcpkg 根目录。
3. **rc / kernel32.lib 找不到**：VS 实例没注册 Windows SDK。解法是 overlay triplet
   + `VCPKG_ENV_PASSTHROUGH RC LIB INCLUDE PATH`（详见 [03](03-环境与构建.md) §3）。
4. **同一构建目录不能同时跑两个编译**：会互相锁 `.obj`（`C1083: Permission denied`）。
   另外杀毒扫新写出的 obj 也会造成随机的 `Permission denied` —— 重跑一次即可。
5. **Debug 构建的 `Q_ASSERT` 会 qFatal**：`SequentialTask::subTaskFailed` 对每个失败子任务都
   `emitFailed`，两个子任务同时失败时第二次会撞上 `ASSERT_NEVER(!isRunning())`。
   Release 只记一条警告，所以上游长期没发现。已在 `SequentialTask` / `ConcurrentTask` 加守卫。
6. **PowerShell 输出习惯**：`… | Select-Object -Last 30` 会缓存全部输出直到命令结束，
   长任务看不到进度；改用 `Tee-Object -FilePath <log>` + `tail`。`Tee-Object` 默认写 UTF-16。
7. **从 Bash 调 `cmd.exe` 可能被安全策略拦**；`.bat` 用 PowerShell 直接 `& ".\xxx.bat"` 更稳。

---

8. **`cmd` 的 `mklink` 不适合在 Qt 里调**：`QProcess` 会按参数逐个加引号，
   路径带空格时 `mklink /J "a b" "c d"` 会被转义坏，报"文件名或目录名语法不正确"；
   自己拼字符串又会踩另一套引号规则。**结论：不做目录联接**，资源迁移直接搬文件 + 改路径解析
   （见 §5 与 [02](02-架构与路线图.md) §2.3）。
9. **AUTOUIC 会把 `ui_*.h` 按包含它的 `.cpp` 所在目录找 `.ui`**：在
   `ui/pages/instance/InstanceSettingsPage.cpp` 里 `#include "ui_MinecraftSettingsWidget.h"`，
   AutoUic 会去 `ui/pages/instance/` 找 `MinecraftSettingsWidget.ui`（实际在 `ui/widgets/`）→ 编译中止。
   要么把构造函数留在头里（用不到）要么走 `findChild<QTabWidget*>("settingsTabs")`，不碰生成的 ui 头。

## 3. Qt / 界面

1. **`QToolBar` 里的 widget 不能用 `setVisible()` 控制显隐**：工具栏会把它从布局摘掉，
   之后 `setVisible(true)` 也回不去。必须走 `QWidgetAction::setVisible()`。
2. **`QGroupBox + QFormLayout` 搬进页签会丢拉伸约束**：先建到顶层再用 `takeAt` 搬运，
   行距会被撑开半屏。内容要**直接建进目标容器**。
3. **`clearReviews()` 别把末尾的 `addStretch` 删了不补**：清空布局后只有一张卡片时，
   它会被拉满整个滚动区（头像在顶、正文到底）。清完立刻补回。
4. **横向滚动条**：卡片里的长行（名字 + 星级 + 日期）会把最小宽度撑大。让元信息单独一行，
   并对评论滚动区设 `setHorizontalScrollBarPolicy(AlwaysOff)`。
5. **组合框宽度**：`setMinimumContentsLength` 是"字符数"，不是像素；设成 4 就会把
   「难度：不限」裁掉。用 `AdjustToContents` + 一个合理的最小像素宽。
6. **颜色不要写死**：深色主题下 `#2e7d32` 的对比度只有 1.6:1。统一走 `MapTheme.h`
   的 `confidenceColor / starColor / mutedTextColor / cardStyle`。

## 4. Minecraft / Agent

1. **`World::repath()` 只在 `suffix()=="zip"` 时走 zip 分支** —— 所以识别层没有复用它，
   而是自带 `LevelDatReader` + `ArchiveReader`，不碰上游代码。
2. **Forge 会把 `System.out` 重定向进 log4j**：Agent 事件从那一刻起收不到，必须
   **自己写日志文件**，宿主轮询 `agent.log`。参数还要落**系统属性**，防止
   LaunchClassLoader 加载出第二份副本读到空配置。
3. **主菜单出现 ≠ 存档落盘**：退出判定必须等 `saveAllWorlds` 的 RETURN 点，且是退出请求之后的保存；
   否则会丢一个自动保存周期。`haltOnSafe=1` 让 JVM 自己退比宿主 kill 可靠。
4. **OptiFine 的列表和 jar 不是一条路**：列表走 BMCLAPI（`/optifine/<mc>`，混着 `preview_*` 要滤掉）；
   下载时 BMCLAPI 会 302 到一个直连被 reset 的域名，官网 `adloadx → downloadx` 带 `Referer` 能取到真 jar。
   所以顺序是 **BMCLAPI（90s，2 次）→ 官网（2 次）**。
5. **旧 `map.json` 的 `requiresExternalModpack` 是误判产物**：`ServerBrands`/`WasModded` 只说明
   作者自己开了模组，不说明存档依赖。判据改成只看 Forge 写在 `level.dat` 里的 `FML LoadingModList`；
   `MapMeta::load` 对旧文件做钳位。

---

6. **1.20+ 的「退出存档后关游戏」只能读日志**：这条轨道没有 Agent（没有符号表），
   拿不到"落盘完成"的回调。可靠信号是服务端的两行英文日志：
   `Stopping singleplayer server as player logged out`（离开存档）与
   `All dimensions are saved`（区块落盘）。看到后者再发 `WM_CLOSE`，
   等不到就 10 秒兜底 —— 存档卡住也不能把玩家永久晾在标题画面。
7. **关游戏用 `WM_CLOSE`，不用 TerminateProcess**：等同玩家点右上角 ×，走游戏自己的退出流程；
   只有 8 秒还不退才回退到 `Application::kill()`。
8. **`runningStatusChanged(true)` 比 `getLaunchTask()` 就绪更早**：`LaunchTask::create()` 里
   `init()` 先 `setRunning(true)` 发信号，之后 `LaunchController` 才把对象写进 `m_launchProcess`。
   于是信号到达时取到的还是**上一次**那个已结束的任务（第一次启动是 `nullptr`，重试能躲过去，
   第二次就静默连到死对象）。凡是「拿到任务再挂日志/挂信号」的逻辑都不能只靠这个信号，
   要么定时核对指针，要么等任务真正的 `start()`。
9. **quickPlay 进图时窗口没有焦点 → 鼠标抓不住**（Mojira **MCL-24083**，重复上报 MC-271193 /
   MC-274999）。MC 在 `screen == null` 那一帧 `grabMouse()`，失败后自己的 `mouseGrabbed`
   已是 true，**不会再重试**；而它只靠「收到过失焦事件」决定要不要暂停，所以窗口从创建起
   就没焦点时既不暂停、也不抓光标。玩家侧的自救是「按一下 Windows 键」或开关一次暂停菜单
   （强制重新 grab）。启动器侧的兜底是**启动后把前台交给游戏窗口**（`MapWindowFocus`）——
   只在本进程仍占前台或压根没有前台时动手，绝不从别的程序那里抢。
   **这条不是本项目的"视角乱转"元凶**，见下一条。
10. **「视角顶死 / 轻微一动就狂转」先查远程控制软件**（ToDesk / 向日葵）。它们的虚拟显示器
   （`ToDesk Virtual Display Device` / `OrayIddDriver`）加输入注入，会让 MC 每帧读到的鼠标增量
   变成一个大常数，表现正是 pitch 卡在 ±90、画面疯狂旋转。2026-11-03 排查了三轮，最后确认
   就是这个原因，**断开远控即恢复**，与启动器无关。
   排查顺序固定成：**① 断开/退出远控 → ② 用官方启动器跑同一个原版实例 → ③ 才怀疑启动器**。
   注意「关掉远控窗口」不等于「断开远控」：服务与 IDD 驱动可能还在，`Get-Service ToDesk_Service`、
   `Get-CimInstance Win32_VideoController` 都能看到它们是否还挂着。

## 5. 已定的决策

| 决策 | 理由 |
| --- | --- |
| **不嵌 Node 引擎**跑 AIO 的 `launcher/src` | 双运行时 + 双错误边界 + 打包体积；AIO 的判断逻辑是纯函数，C++ 重写才划算 |
| **符号表离线生成、运行时只读** | 实时解析要扫 jar，秒级开销；AIO 已经算好了，直接当静态资源 |
| **不重写符号解析器到 C++** | 工作量 ×3，收益为零 |
| **实例目录名沿用 Prism 的"名称派生"** | 改 `InstanceStaging` 会波及实例列表/快捷方式；AIO 自己 v0.28 改 UUID 又回滚了 |
| **世界目录固定 `MapWorld`** | quickPlay 与 Agent 都吃字符串；老版本对中文路径有坑 |
| **`map.json` 独立于 `instance.cfg`**，`notes.json` 再独立一层 | INI 表达不了数组与证据链；"这张图是什么"（自动）与"我怎么看这张图"（人写）必须分开存 |
| **UI 融入原生，不另起模式**（双模式 `QStackedWidget` 已按用户要求移除） | 地图信息区插进原生实例操作栏，`Application::m_mainWindow` 的 25 处引用零改动 |
| **启动准备挂在 `Application::launch`，不挂在主窗口** | 启动入口有五个，漏一个就会让老版本静默停在主菜单 |
| **traits 没解析出来时不判轨道**，只写世界名让游戏按自己的 trait 决定 | 启动瞬间组件尚未加载，`traits()` 是空的；硬判会把 1.21 误判成"不支持 quickPlay"，顺手清掉 `JoinWorldOnLaunch`，游戏停主菜单 |
| **启动后把前台交给游戏窗口**（`MapWindowFocus`） | quickPlay 在无焦点时抓不住鼠标（MCL-24083）；只在"前台还是我们"或"没有前台"时动手，不抢用户的焦点 |
| **下载一律交系统浏览器** | AIO §40 的教训：Cloudflare 只认可见浏览器，七种"藏窗口"方案全失败 |
| **Agent 用 `haltOnSafe=1`（JVM 自己退）** | Prism 侧没有"落盘完成"概念，宿主 kill 时机靠猜 |
| **被封 SNI 的站一律借本机浏览器**，不在 C++ 里实现 ECH/QUIC | Qt 在 Windows 走 Schannel，没有 ECH；自己实现等于重写 TLS 栈 |
| **大厅整库本地化，点开只读本地** | 每个请求都要借浏览器，现拉一次十几秒；本地化之后搜索/详情/评论是毫秒级 |
| **不复活"一个高版本核心通吃"** | 1.13 / 1.16~1.20 / 1.20.5 三次语义断裂，DFU 不翻译命令方块 |
| **"实验性设置"确认页用运行时补丁跳过，绝不动世界数据** | `DataPacks.Enabled` 里的自定义生物群系被摘掉会让已生成区块失去引用（坏档）；改 `pack_format` 也没用 —— 判定依据是包内容不是版本号。补丁只把 `WorldOpenFlows.askForBackup` 的方法体换成 `loadLevel.run()`（[06](06-变更记录.md) §18） |
| **`-javaagent` 走运行时属性，不写 `JvmArgs`** | `JvmArgs` 是 override 设置：`OverrideJavaArgs=false` 时实例里写的值**永远读不到**，quickboot 曾因此静默失效（[06](06-变更记录.md) §18.4） |
| **Agent / Java 侧的日志路径必须纯 ASCII** | 中文 Windows 的 `sun.jnu.encoding=GBK`，实例名里的 `Ξ` 会让 `FileWriter` 直接抛"找不到路径"，日志静默丢失（[06](06-变更记录.md) §18.4） |
| **下载源只在 HTTP 层改写一次、映射表之外不猜** | 改在 `Net::Request::executeTask()` 一处覆盖资源 / 库 / 版本 json / 运行时清单；重定向回不到映射表所以不会二次改写。Modrinth / CurseForge 是数据接口，镜像里没有，**永不映射**（[06](06-变更记录.md) §26） |
| **镜像请求直连，不继承启动器代理** | BMCLAPI 会 302 到各 OpenBMCLAPI 节点，代理会把这些跳转掐掉（实测）；镜像换用 `QNetworkProxy::NoProxy` 的独立 QNAM |
| **Atlas 不做自更新、不订阅上游新闻** | 更新器指向的是上游仓库，装上等于把自己覆盖成 Prism；"Prism Launcher Release x.y.z, now available"是上游 RSS 的标题，不属于本启动器（[06](06-变更记录.md) §21） |
| **镜像节点抖动靠重试，不做节点池** | BMCLAPI 单次成功率仅 30–50%（302 到随机节点，部分不可达），重试是唯一对策；节点池等于自己维护一份镜像拓扑（[06](06-变更记录.md) §28） |
| **重试必须回到镜像入口，不是重试失败的那个节点** | 302 之后 `m_url` 已是节点域名，接着打同一个节点等于确定性失败；回到入口才会重新 302 到另一个节点。封顶 3 次（每次都要重下整个文件），只认连接层错误 —— 拿到 4xx/5xx 就停手（[06](06-变更记录.md) §29.2） |
| **`FileSink` 重入 `init()` 是"截断重写"，可以放心重试** | `QSaveFile` 先写 `<目标>.XXXXXX`、`commit()` 才改名，所以半截数据既不会 append 到下一轮，也不会毁掉目标位置上原有的好文件。已由 `RequestRetry_test` 的三个写入时序用例钉住，别改成直接写目标文件（[06](06-变更记录.md) §29.1） |
| **传输超时（`OperationCanceledError`）不是"用户取消"** | `RequestTimeout` 到期时 Qt 会 abort 掉 reply，报的和"用户点了中止"一模一样。用户取消走 `Request::abort()`（先断 `errorOccurred`），进不到错误处理；所以能收到的取消只能是超时，必须按可重试的网络故障处理（[06](06-变更记录.md) §30） |
| **文件下载走 HTTP/1.1，JSON/API 仍用 h2** | 一条 h2 连接跑 6 个大文件时会互相饿死：实测同一条连接上一条流 75 秒下完、另一条 60 秒零字节，零字节那条被超时掐掉。h1.1 每个文件一条连接，互不牵连；6 并发总吞吐实测两者一致（1.86 MB/s），所以没有性能代价（[06](06-变更记录.md) §30） |
| **镜像彻底失败后回落官方一次，且只单向** | 用户选镜像是为了快，不是为了"宁可不下载"；但官方失败不能反向切镜像（那条路上文件更可能下不下来）。回落判定写成纯函数 `shouldFallBackToOfficial()`，单测钉住不绕圈（[06](06-变更记录.md) §30） |
| **下载走 QNAM 池，不是提高并发数** | Qt 一个 QNAM 每主机固定 6 条 HTTP/1.1 连接（公开 API 改不了），并发数调到 64 也只会排队。4 个 QNAM 才真的开出 24 条；实测同一批文件 209 → 467 KB/s。2026-11-06 起池子是 8 个（48 条），因为这条线路是「每连接 10–25 KB/s」（[06](06-变更记录.md) §31、§41） |
| **连接池只给文件下载，JSON/API 留在主 QNAM** | 池是轮转的，把接口请求也扔进去等于把会话/cookie 拆到几个罐子里；下载只需要连接 |
| **大文件分段：先丢原连接，再发 N 条 Range** | 决定拆段时那条无 Range 的响应会把整个文件拉回来，写进第 0 段时覆盖别的分片 —— 必须 abort 掉重开。段数不超过字节数（否则出现长度 0 的分片，Range 直接 416）（[06](06-变更记录.md) §32） |
| **分段写入必须在 finalize 时重算校验** | 分片乱序写盘，校验器拿不到连续字节流；`finalize()` 把 `.part` 按顺序读一遍喂给校验器，不通过就不 rename —— 目标位置原有的好文件绝不能因为一次失败的下载被毁 |
| **分片的重试只能有一个入口** | `errorOccurred` 之后必然跟一个 `finished`；两处都调重试等于一次失败花掉两次预算（实测 3 次上限只剩 1.5 次，5 秒就整体降级）。只在 `finished` 里决定 |
| **分片失败从断点续，不整片重下** | `Range: bytes=<已收>-<片尾>`；弱网下一片几 MB，断了从头来等于白干（[06](06-变更记录.md) §33） |
| **绝不在 reply 自己的信号里析构它** | 决定拆段时要丢掉无 `Range` 的那条响应，曾在 `metaDataChanged` 槽里 `reset()`：QNAM 之后所有请求静默挂死（8 个分片一个信号都不回）。必须 `release()` + `abort()` + `deleteLater()` |
| **拆段阈值 4 MB，不是 1 MB** | 1 MB 的库拆 8 段是负收益：请求数 ×8、TLS 握手 ×8，实测把对端连接数打到 190+。≥4 MB（client jar / fastutil）才拆（[06](06-变更记录.md) §35.2） |
| **死连接要有独立闸门** | 服务器不回包也不断开时，Qt 的传输超时只会在 `RequestTimeout`（默认 60 秒）后触发；一个 20 KB 的 json 卡一分钟，用户看到的就是"卡死"。建好 reply 就起 20 秒表；**收到响应头后不停表，而是重新起表**——只守响应头会漏掉"有头无 body"（[06](06-变更记录.md) §37、§39） |
| **换源回落必须双向且互斥** | 只有"镜像→官方"时，选了官方源又遇上 `piston-meta` stall 就毫无退路；两个方向各一次并互相排斥，才不会绕圈（[06](06-变更记录.md) §37） |
| **"慢"和"卡死"要分开判** | 传输超时只认完全没数据；20 KB/s 的龟速界面看起来一样死。按 10 秒窗口统计吞吐，连续 2 次低于 15 KB/s 就换连接（单连接最多 3 次；**分片按片判、每片最多 2 次**）（[06](06-变更记录.md) §38、§39） |
| **空闲看门狗必须覆盖整条传输，不能只守响应头** | "收到 200 之后 body 再也不来"是最常见的挂死形态：Qt 的传输超时在这种情况不一定触发，实测一个请求挂了 3542 秒（[06](06-变更记录.md) §39）。所以建好 reply 起表、**每收到一次数据重新起表**，20 秒没有字节就掐 |
| **分片的"慢"要在片这一级判，并保留断点** | 分片模式曾经完全绕过吞吐看门狗（`m_parallel` 直接 return），12 条连接各 13 KB/s 时日志一行都没有。慢片 abort 后走 `retryChunk` 从断点续，不丢已下载的字节；换两次还慢就放行，避免耗光 attempts 被降级成单连接（[06](06-变更记录.md) §39） |
| **顺序下载一律写 `<目标>.part`，不用 QSaveFile 的隐藏临时文件** | 只有"看得见、留得住"的临时文件才能续传：`QSaveFile` 的临时文件在 `abort()` 时就没了，弱网下等于永远重来（[06](06-变更记录.md) §36） |
| **续传必须把已有字节补喂校验器** | 校验器是流式哈希，只喂新数据算出来必然不对；`init()` 时把 `.part` 读一遍再继续 |
| **服务器无视 Range 就 `restartFromZero()`** | 带了 Range 却收到 200 意味着"整份内容"，继续 append 会得到内容 ×2 的文件 |
| **分片 scratch 用 `.part.parallel`，与断点文件分离** | 分片是"预分配到总长度 + 空洞"，顺序断点是"从 0 开始的连续前缀"；混用会把空洞当数据（[06](06-变更记录.md) §36.5） |
| **分片失败先减半段数重试，再退回单连接** | `libraries.minecraft.net` 会随机关闭并发连接，被掐的那片两次零进展就整体降级成单连接，等于把 12 倍带宽丢成 1 倍（一个 23 MB 的 jar 爬了十几分钟）。现在先 12 → 6 再试一次，仍失败才单连接（[06](06-变更记录.md) §43） |
| **单片连续 3 次零进展不算"越界"，先减半段数** | 某些主机（piston-data）会对某一段持续不理人，每次都要 60 秒超时、重试仍是同一偏移；硬试 6 次 = 6 分钟白等（[06](06-变更记录.md) §35.3）。阈值从 2 提到 3，是因为 `libraries` 会随机关连接，两次就放弃太急（§43） |
| **文件下载强制走 QNAM 池，忽略 NetJob 塞进来的主 QNAM** | `NetJob::addNetAction()` 会给每个请求 setNetwork(主 QNAM)，只要"为空才挑池"，池就永远用不上（[06](06-变更记录.md) §35.1） |
| **同一个目标文件同时只允许一个 sink 用 `.part`** | 两个组件会并行拉同一个 `meta/index.json`，共用 `.part` 会互相覆盖；416 之后删不掉（被对方打开）→ Range 越界 → 重试 → 还是越界，几秒烧完预算、安装失败（[06](06-变更记录.md) §41）。第二个 sink 退到 `<目标>.part-<id>`，分片 scratch 同理 |
| **下载观测做成旁路，不让下载逻辑认识 UI** | `NetJob` 只在构造/析构时登记到 `DownloadMonitor`，界面 500ms 轮询取快照；删掉界面不影响网络层（[06](06-变更记录.md) §41） |
| **下载总速度必须从活跃个体增量累加，不可用总量相减** | 活跃文件一旦下载完毕移出快照，活跃总量会骤降十几 MB，直接做差值导致瞬时速度出现巨额负数打崩平滑值并清零仪表盘（[06](06-变更记录.md) §44） |
| **`FileSink` 异常退出时必须即时释放 part 占用** | 尽管析构函数有 RAII 保障，但重试与异常退出若未及时归还 `s_partOwners`，会导致后续请求误判冲突并多退一步（[06](06-变更记录.md) §44） |
| **资源目录用真路径，不用 junction** | 迁移后就是普通目录，备份/换机器/给别的启动器复用没有隐性依赖；代价是改完要重启 |
| **地图/资源设置并进设置页**，不维护独立对话框 | 一半设置本来就是启动器级的；两份 UI 必然漂移 |
| **双轨导入（地图与整合）必须在入口层隔离并通过 UI 把终极选择权归还给玩家** | 压缩包内容千差万别（整合包可能内置地图模板，地图存档包也可能携带模组与材质）；私自单向拦截会剥夺用户意图并引发误建实例。必须在拖拽入口（`ImportChoiceDialog`）与新建实例导入页（`ImportPage` 单选切换）全覆盖，并提供双向智能建议（[06](06-变更记录.md) §45） |
