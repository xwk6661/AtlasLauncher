## 3. 四个环境坑（都已解决，按这个来）

| # | 坑 | 现象 | 解法 |
| --- | --- | --- | --- |
| 1 | vcpkg 的 git 注册表要完整历史 | 浅克隆 `microsoft/vcpkg` 到 63 MB 停滞 | 把本地浅克隆当 **builtin 注册表**：manifest 加 `builtin-baseline`，`vcpkg-configuration.json` 用 `{"kind":"builtin","baseline":…}` |
| 2 | vcpkg 要 pwsh 7.6.9 | 卡在下载 `PowerShell-7.6.9-win-x64.zip`（109 MB） | 16 线程分段下载 → 校验 SHA512 → 放进 `vcpkg/downloads/`；lzo / bzip2 同理从清华镜像取（哈希一致即可） |
| 3 | **VS 实例没注册 Windows SDK** | 端口构建报 `rc` 找不到、`LNK1104: kernel32.lib` | overlay triplet + `VCPKG_ENV_PASSTHROUGH RC LIB INCLUDE PATH`（见下） |
| 4 | 上游 Java 子项目用 `-source 7` | `错误: 不再支持源选项 7` | 预设里把 `Java_JAVAC/JAR/JAVA_EXECUTABLE` 指向 JDK 8 |

**坑 3 的关键**：vcpkg 给端口构建的是**干净环境**，进程内改 `PATH`/`RC` 传不进去；而本机
`Enter-VsDevShell` 之后 `WindowsSdkDir` 是空的。所以用本地 overlay triplet：

```cmake
# E:/Program File/vcpkg-manifests/prism/triplets/x64-windows.cmake（不进仓库）
include("<仓库根>/cmake/vcpkg-triplets/x64-windows.cmake")
set(VCPKG_ENV_PASSTHROUGH RC LIB INCLUDE PATH)
```

**⚠ ABI 哈希**：`RC` / `LIB` / `INCLUDE` / `PATH` 都参与 vcpkg 的 ABI 哈希。
`run-vcpkg.ps1` 与 `run-configure.ps1` 必须 dot-source **同一份** `env-toolchain.ps1`，
否则每换一次环境就把 18 个依赖重编一遍（11–20 分钟）。

## 4. 沙箱 / 自动化环境下的临时配方

在受控沙箱里跑 `cmake --preset` 会触发 vcpkg 重装依赖，而安全策略**拦掉了 `reg.exe`**：

1. `vcvars64` / `Enter-VsDevShell` 静默失败 → 只设了 MSVC 的 `INCLUDE`/`LIB`，**没有 Windows SDK 路径**；
2. cmark 的 try-compile 依次挂在 `rc` 和 `kernel32.lib` 上，vcpkg 顺手把 `vcpkg_installed` 清空；
3. 于是整棵工程不可编译。

临时解法：`build/_build_env.cmd` 手工写全 `INCLUDE`/`LIB`/`PATH`（**SDK 在前、MSVC 在后**）再 `cmake --preset`，
可稳定出包。代价是 ABI 哈希与 `env-toolchain.ps1` 不一致 —— **接手后先跑一次 `build/run-vcpkg.ps1` 归一**，
之后照 §2 走，否则每次都会全量重编。

另一个反复出现的干扰：链接大文件（`LauncherTests.exe` 28 MB / `.pdb` 280 MB）时偶发
`C1083: Permission denied` 或链接挂起十几分钟，重跑即可，**不是代码问题**。
`C1083` 也可能出现在编译阶段（报"无法打开编译器生成的文件 … .obj"）：同样的源码单独编能过、
下一次重跑也能过，属于写 `.obj` 时的瞬时占用，不是 ACL 或磁盘问题（实测 `-j1` 串行也会偶发一次）。

### 4.1 沙箱里 vcpkg 端口构建会卡死（2026-11-03 实测）

在受管沙箱内跑 `cmake --preset` 时，用 **CMake** 构建的端口（cmark / ecm / zstd / libarchive…）正常，
但用 **autotools** 的端口（`lzo` 等）会停在 `-- Configuring x64-windows` 不动：
`configure` 依赖 vcpkg 自带的 msys2 环境，沙箱会拦掉其中的子进程（同一次运行里还能看到
`reg.exe` 被 Program Blacklist 拒绝）。现象是 `cl.exe` 常驻 0 CPU、`config-*-out.log` 一直为空。

解法：把 `cmake --preset` / `cmake --build` 放到沙箱外跑一次（本机实测 15 个包 10 分钟装完，
其中 `lzo` 只需几秒）。**不要**因为卡住就判定"依赖装坏了"。

## 6. 产物与数据目录（便携模式）

`build\win-local\Debug\` 同时是**运行数据目录**：exe 旁有 `portable.txt`，所以
`atlas.cfg`（改名前的 `prismlauncher.cfg` 已复制过来，原文件保留作备份）、
`instances\`、`maps\`（库 + 大厅缓存 + 封面缓存）、`accounts.json` 都在这里。

**不要对 `build` 目录做 clean** —— 那会连玩家数据一起删掉。

数据目录里还有三份**跨实例共享**的资源：`assets/`、`libraries/`、`java/`。
第一次进某个版本时，`java/` 会从 `piston-data.mojang.com` 拉一份 Mojang 官方运行时
（1.21 约 400 个文件 / 150 MB）—— 这是正常的，不是重复下载游戏本体。

想把这三大块挪到别的盘：**设置 → 资源** 选目录 → 应用资源库（同盘瞬间完成，跨盘复制后删源）→
**重启启动器**。迁移逻辑见 [02](02-架构与路线图.md) §2.3。

## 8. 仓库外动过什么（可撤销）

| 位置 | 改了什么 | 为什么 |
| --- | --- | --- |
| `…vcpkg-manifests/prism/vcpkg.json` | 加 `builtin-baseline` | 坑 1 |
| `…prism/vcpkg-configuration.json` | `builtin` 注册表 + 本地 overlay triplet | 坑 1 |
| `…prism/triplets/x64-windows.cmake` | 新增，透传 RC/LIB/INCLUDE/PATH | 坑 3 |
| `E:/Program File/vcpkg/downloads/` | 手工放入 pwsh / lzo / bzip2 源码包 | 坑 2 |
| `CMakeUserPresets.json`（gitignore） | ninja / rc / cl / JDK8 的绝对路径 | 坑 3、4 |
| `build/*.ps1`、`run-atlas-debug.cmd`、`_build_env.cmd` | 一键复现 | — |

> **仓库目录改过名（`PrismLauncher` → `Atlas` → `AtlasLauncher`）时，仓库外这几处必须同步改**，
> 否则 configure 会挂在 `Overlay path … must be an existing directory` 或
> `include could not find requested file: …/cmake/vcpkg-triplets/x64-windows.cmake`：
> `…prism/vcpkg-configuration.json` 的 `overlay-ports` / `overlay-triplets`、
> `…prism/triplets/x64-windows.cmake` 里的 `include(...)`。仓库内的 `build/*.ps1` 已改为按
> `$PSScriptRoot` 推导，不用再改。CMake 还会把旧源码路径写进 `build/win-local/CMakeCache.txt`
> 与 `CMakeFiles/impl-*.ninja`，改名后必须重新 configure（见 [06](06-变更记录.md) §11）。

**没有**改注册表或系统环境变量。
